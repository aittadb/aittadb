# Performance

AittaDB keeps public discovery and static delivery off the database path. Requests for `/`, `/health`, discovery, JWKS, OpenAPI, docs, `/auth-ui.css`, and `/auth-ui.js` do not issue D1 statements. Static assets bypass application creation and pass directly to Vinext.

Durable routes construct the D1 repository but never apply schema DDL. Independent client redirect, scope, and origin lookups are hydrated concurrently. Expired-row cleanup is non-authoritative and scheduled through a rejection-catching promise passed to `waitUntil` at most once per one-minute Worker instance interval, so a response does not wait for cleanup and correctness never depends on process memory. Each run removes at most 500 rows from each eligible OAuth, device, refresh, revocation, admin-submission, audit, and rate-counter category, ordered by the oldest eligibility timestamp and then `rowid`. Expired file-write fences use a separate limit of 25. The fixed cleanup report accepts a deleted count only from successful D1 mutation metadata containing a nonnegative safe integer within that category's limit; missing or malformed metadata is explicitly unverifiable rather than assumed to mean zero. The same interval processes at most 25 file-orphan candidates using an indexed deterministic order; failures move behind older work. One-minute rate counters remain eligible for reuse or inspection for five minutes before cleanup.

One internal account-file purge call stages at most 25 deterministic metadata rows in one transactional D1 batch and processes at most 25 subject-owned repair candidates. Large accounts therefore require repeated bounded calls; no request performs an unbounded namespace or R2 sweep.

Storage collection queries return at most the configured `page_size` plus one look-ahead row, initially 50 by default and 100 at maximum. The response returns no more than `page_size` items. For an unchanged record or file collection, following only returned `next` links visits every authorized logical item exactly once. File pages return D1 metadata only and never physical R2 keys; bounded integration fixtures verify that each listed file still resolves to matching R2 bytes and digest. Encrypted cursors preserve deterministic ordering without an unbounded list or server-side cursor table. Request readers enforce byte bounds while consuming streams, before complete parsing, which bounds buffering but does not turn large accepted uploads into zero-copy transfers.

Accepted URL-encoded and JSON request bodies are normally prebuffered once through the shared streaming reader before CORS client lookup, rate limiting, authentication, parsing, or repository access. `POST /storage/record-protocol/transactions` is the narrow exception: after its Records feature and browser-origin gates, its CORS decision and existing finite storage IP/deployment admission run before either accepted body is pulled. An exhausted transaction admission returns fixed `429 slow_down` with `Retry-After: 60` without token verification, command decoding, or record/receipt lookup; an admitted request then follows the normal bounded reader and its existing authenticated namespace write admission exactly once. A valid declared length above the route limit fails without pulling the body. Missing, malformed, or deliberately undersized `Content-Length` values are ignored as authority: the byte count observed from the stream still enforces the limit and cancels on the first overflowing chunk. The bounded request is reconstructed for the existing parser, so parsing and domain validation remain route-owned. This bounds memory but does not make accepted bodies zero-copy. Bounded transaction command body failures, including overflow, use that protocol's fixed `400 invalid_request`; other routes advertise their own fixed malformed-body and overflow response codes.

Canonical bearer file `POST` and `PUT` requests use that same bounded reader at the 10 MiB file limit after access-token authorization and before hashing, R2 writes, or D1 file-metadata work. Declared overflow cancels without a pull; absent, malformed, undersized, and chunked lengths remain bounded by observed bytes. Stream failure returns `400 invalid_request`, while actual overflow returns `413 invalid_request`. Browser multipart wrappers retain their separate identity-first aggregate bound and then pass only the extracted file bytes through this canonical path.

Rate limits use one atomic D1 upsert per counter. Endpoint families apply hashed per-IP counters and a global ceiling ten times the per-IP value; storage adds a local-user/client read or write counter. New counter keys fail closed when the table reaches 10,000 rows, bounding cardinality at the cost of rejecting new principals until cleanup creates room. Record and file writes also evaluate deployment, user, and namespace item/byte totals in one conditional D1 statement. Those aggregate checks favor correct abuse ceilings over minimum write latency and should be benchmarked against the expected data volume before raising the finite defaults.

Event long polling is intentionally database-backed rather than process-memory-backed. A request waits at most 25 seconds by default, performs at most 26 namespace-scoped indexed reads, stops when its request signal is cancelled, and has a separate admission counter before waiting. Operators can lower the configured wait/read ceilings; hard maxima are 30 seconds and 31 reads. This trades some bounded D1 traffic for correct delivery across independent Worker isolates and avoids durable correctness depending on an in-memory notifier or background process.

Before this boundary was introduced, single live checks on 2026-08-07 measured approximately 3.96 seconds to first byte for `/`, 5.61 seconds for `/health`, and 4.04 seconds for `/auth-ui.css`, while a static SVG returned in 0.07 seconds. The shared cause was sequential schema creation on every dynamic request.

After deployment, first observed dynamic responses measured approximately 1.73 seconds for `/` and 4.11 seconds for `/health`; warm checks measured 0.32 seconds and 0.19 seconds respectively, with `/auth-ui.css` at 0.22 seconds and the static SVG at 0.11 seconds. The final 34-request HTML/JSON route matrix returned warm first-byte times between 0.07 and 0.31 seconds. The unauthenticated method matrix returned expected fail-closed responses between 0.07 and 1.31 seconds. Error-filtered Worker logs contained no exception outcomes; observed entries were expected 4xx acceptance probes, default favicon misses, and client-cancelled file-response events after the signed-in upload/list/download/delete checks completed successfully. These observations are diagnostic evidence for an earlier deployed revision, not a latency SLA or live verification of the current TASK-075 through TASK-086 controls.

Performance changes must preserve security and durability. Do not cache identity, grants, tokens, consents, client disablement, or storage ownership in process memory, and do not weaken no-store responses, token validation, rate limits, or per-user/per-client query predicates to reduce latency.
