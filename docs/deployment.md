# Deployment Guide

Private deployment testing must wait for explicit maintainer approval.

Before creating a private Sites deployment:

1. Generate a unique protected signing-key candidate with `make generate-local-jwt-key`, then validate it as documented in `docs/key-rotation.md`.
2. Create a fresh Sites project for the fork.
3. Copy `.openai/hosting.example.json` to `.openai/hosting.json` and replace the placeholder with that new Sites project ID.
4. Configure D1 binding `DB`.
5. Configure R2 binding `BUCKET` for AittaDB object storage.
6. Configure hosted values for `ISSUER_URL`, `JWT_KEY_ID`, `JWT_PRIVATE_JWK`, the privacy notice, and the storage controls documented in `.env.example`. Leave `ADMIN_SUBJECTS` empty until the intended administrator has signed in once.
7. Run `npm run validate`.
8. Inspect `dist/.openai/drizzle/` and confirm it contains one generated SQL artifact for every reviewed file in `db/migrations/` plus a non-empty migration journal.
9. Deploy privately only after explicit approval.

## Public Sites Access

AittaDB treats public Sites access as a supported operating posture, not as authorization. Public mode permits any ChatGPT user to reach the Sites sign-in boundary and create a separate local AittaDB identity. It must never make another subject's session or storage, administrator operations, internal tables, bindings, signing material, or hosted secrets public.

Review privately first, then make a deployment public only with explicit approval. Before and after that change, verify an unauthenticated control can read only intended public resources, two ordinary signed-in users receive distinct empty namespaces, cross-user reads remain non-disclosing, and an unallowlisted user cannot administer the service. Keep finite global/user/namespace quotas, endpoint and storage rate limits, feature gates, and `STORAGE_WRITES_ENABLED` configured for abuse containment. Public access never substitutes for these server-side controls.

Keep `.env`, `.dev.vars`, `.secrets/`, `.wrangler/`, and active `.openai/hosting.json` data local or in hosted configuration. Do not commit real `.openai/hosting.json` production `project_id` values as part of reusable public templates. Sites project IDs are public deployment identifiers rather than credentials, but reusing one still violates deployment isolation. Run `npm run secrets:check` before review; release secret-safety acceptance uses `npm run secrets:audit-history` from a complete clone and prints only category, path, and commit for findings.

The build configuration falls back to `.openai/hosting.example.json` so type checking and production-build validation work in a clean checkout and in CI. This fallback does not configure a deployable Sites project. A real deployment still requires the ignored checkout-local `.openai/hosting.json` created in step 3.

Forks must create their own Sites project, D1 database, R2 bucket, JWT signing key, and hosted secrets. Do not reuse another deployment's `.openai/hosting.json`, signing key, administrator allowlist, D1 database, or R2 bucket. Signing-key rotation is an approved single-key cutover and rollback operation; follow `docs/key-rotation.md` rather than generating or printing replacement material ad hoc.

## Administrator Bootstrap and Migration

For a fresh deployment, leave administration closed while `ADMIN_SUBJECTS` is empty. Sign in at `/session` to create the local user and read its immutable deployment-local AittaDB UUID. Add that canonical UUIDv4 to `ADMIN_SUBJECTS` through Sites configuration and deploy the configuration change. The next request from that same trusted Sites session can open `/admin/clients` directly; no separate administrator password, key, header, or unlock cookie exists.

For an existing deployment using the removed `ADMIN_EMAILS` or `ADMIN_ACCESS_KEY_HASH` settings:

1. Before upgrading, sign in with each intended administrator and record only the local UUID shown by `/session`.
2. Configure those UUIDs in `ADMIN_SUBJECTS` and deploy the new source and configuration together.
3. Confirm that an allowlisted signed-in account can open `/admin/clients` and an unlisted account receives a generic denial.
4. Remove the obsolete `ADMIN_EMAILS` and `ADMIN_ACCESS_KEY_HASH` hosted values; the new source never reads them.

Administrative mutations are audited with bounded action data and hashed actor/client references. Do not claim that UUID allowlisting fixes reassignment: AittaDB still locates the local UUID through the upstream email, so a reassigned address can resolve to the same subject. Until Sites supplies a stable upstream subject or AittaDB gains a stronger account-migration contract, operators must treat that as a material residual administrator-takeover risk and keep the allowlist narrow.

## Privacy Notice Configuration

The operator of each published AittaDB deployment is the controller for that deployment's Hosted Data and must review the [baseline Privacy Policy](privacy.md), applicable law, configured OAuth clients, purposes, retention, and contact details before publishing. OpenAI hosts and processes Sites Hosted Data under the applicable [ChatGPT Sites Data Processing Addendum](https://openai.com/policies/chatgpt-sites-data-processing-addendum/) or the operator's organization agreement. Do not claim a fixed processing location: [Sites documentation](https://help.openai.com/en/articles/20001339-creating-and-managing-chatgpt-sites) currently says deployed Sites, D1/R2 data, artifacts, and logs do not support data residency at launch.

Configure only public values in `PRIVACY_CONTROLLER_NAME`, `PRIVACY_CONTROLLER_IDENTIFIER`, `PRIVACY_CONTACT_NAME`, `PRIVACY_CONTACT_EMAIL`, `PRIVACY_CONTACT_PHONE`, and `PRIVACY_CONTACT_ADDRESS`; explicit values take precedence and blanks are not rendered. Do not put credentials or private addresses in these fields. No personal defaults belong in source control.

When required controller/contact data is incomplete, `/privacy` resolves the first canonical UUID in `ADMIN_SUBJECTS` through the local-user repository and uses only its last stored email plus optional display name. It never displays that UUID, the allowlist, or another user field. This fallback works only after that administrator has signed in, does not prove that the address remains current or verified, and still carries the documented email-reassignment risk. If neither explicit configuration nor the fallback yields a usable controller and contact, `/privacy` returns a generic `503` rather than an incomplete notice.

Before publication, request `/privacy` with both `Accept: text/html` and `Accept: application/vnd.aittadb+json; version=0.1`; verify the same policy and links, escaped intended contact values, and no identifier or secret leakage. Repeat this review whenever the operator, clients, purposes, retention, Sites terms/DPA, or contact configuration changes.

## AittaDB Storage Controls

Set `FEATURE_RECORDS_ENABLED=false` when a deployment must not expose JSON Records. The entire `/storage/records` route family then returns a content-negotiated `503 feature_unavailable` before any repository operation, and Records links/actions disappear from service, session, and file-storage discovery. This flag does not disable Files, Statistics, health, privacy, or the internal signed-in session.

Leave `FEATURE_OAUTH_APPS_ENABLED=false` until downstream interactive or service OAuth clients are intentionally enabled. Client administration, Authorization Code, Device Grant, Client Credentials, their browser continuations, `/oauth/token`, `/oauth/revoke`, `/oauth/introspect`, and `/userinfo` then reject before body reading, bearer or identity lookup, CORS/client/credential lookup, rate limiting, cleanup, or mutation. Application resources return content-negotiated `503 feature_unavailable`; OAuth POSTs return no-store `temporarily_unavailable` where the protocol requires it. Their controls disappear from service and session representations. Discovery retains only `issuer`, `jwks_uri`, and `id_token_signing_alg_values_supported: ["ES256"]`; it advertises no disabled grant or UserInfo operation. JWKS remains public and publishes only the configured public P-256 key so private AittaDB session JWTs remain verifiable. The private reserved client remains available only for AittaDB's signed-in session and enabled storage operations.

Set `FEATURE_FILES_ENABLED=false` when a deployment must not expose File Storage. The entire `/storage/files` route family then returns the same negotiated `503 feature_unavailable` before client lookup, authentication, rate limiting, request parsing, D1 file-metadata work, R2 access, or cleanup scheduling. File links/actions disappear from service, session, and record-storage discovery. Records, Statistics, health, privacy, and the internal signed-in session remain available.

`FEATURE_EVENTS_ENABLED` is a strict, default-off deployment-policy flag. In the current implementation its effective value appears in service HTML and hypermedia metadata, but enabling it does not add or advertise an Events route, scope, link, action, or persistence operation. Keep it false until the Events endpoint tasks are complete. Those routes must enforce the flag at their outer boundary before body, bearer, identity, rate-limit, repository, or maintenance work.

The initial finite defaults combine records and files and enforce 10,000 items/1 GiB deployment-wide, 1,000 items/100 MiB per local user, and 500 items/50 MiB per local-user/client namespace. Configure lower values for a restricted beta when appropriate. These are AittaDB-enforced abuse ceilings, not Sites quotas or capacity promises. Storage collection pages default to 50 items and reject values above the configured maximum of 100. Per-namespace storage read/write defaults are 120/30 operations per minute.

Set `STORAGE_WRITES_ENABLED=false` as an operational kill switch when new or replacement storage must stop. Signed-in and signed-out HTML plus versioned hypermedia omit record/file create and replacement controls, including on missing-resource pages. Direct canonical and browser-adapter writes still return the non-persisting `503 storage_writes_disabled` response. Authorized reads and deletes remain available so users can inspect or reduce usage. A configured item/byte ceiling returns `507 storage_limit_exceeded`. Collection usage output contains only the caller's current user/client namespace, never global or cross-client totals.

Rate counters use one-minute windows. A global endpoint-family ceiling is ten times its per-IP ceiling. The counter table fails closed for new keys at 10,000 rows; once-per-minute background cleanup removes at most 500 rows per category, oldest eligibility timestamp first with a deterministic `rowid` tie-breaker, and keeps rate-counter rows for five minutes. Monitor sustained `429` responses because cleanup is bounded and depends on durable-route traffic and `waitUntil` execution.

`MAINTENANCE_CLEANUP_TELEMETRY_ENABLED` is a strict, default-off operator control for private Worker logs. Enable it only for an approved cleanup acceptance window, trigger an ordinary durable request, and inspect the provider's private logs for one fixed `maintenance.cleanup.completed` event containing only semantic category, verified deleted count (or `null` when D1 metadata cannot verify it), and configured batch limit. Cleanup failures always emit only `maintenance.cleanup.failed`; no exception, query, identity, request, or deployment value is attached. Disable the flag after collecting evidence. There is deliberately no HTTP, administration, hypermedia, OpenAPI, or fixture-generation interface for this telemetry.

## Public-Beta Limits

As of August 8, 2026, Sites usage is included up to plan-specific public-beta limits. **Persistent D1 database and R2 object storage are provided by ChatGPT Sites, subject to the plan-specific aggregate limits displayed in ChatGPT during the public beta.** Limits apply across all Sites on the account, may change, and can vary for Enterprise and Edu workspaces. ChatGPT displays the limits available to the current plan or workspace and warns as usage approaches them. At a limit, an operator may be unable to add storage, create another Site, or keep a high-usage Site publicly available until usage is reduced. Check [Creating and managing ChatGPT Sites](https://help.openai.com/en/articles/20001339-creating-and-managing-chatgpt-sites) before sizing or publishing a deployment.

OpenAI currently publishes no numerical Sites D1/R2 capacity or allocation, per-object size, row or query, bandwidth or operation, or additional-pricing figures. Treat the limits shown in the Sites experience as authoritative and do not promise fixed AittaDB capacity. The Pro plan's 100 GB [ChatGPT Library](https://help.openai.com/en/articles/20001052/library-for-chatgpt) quota is for ChatGPT Library files and is unrelated to Sites D1/R2.

Sites applies D1 migrations from the packaged deployment artifact. Migration `0004_security_indexes.sql` adds cleanup/origin indexes and scrubs legacy short device user-code display values; only the hash remains durable. Migration `0005_admin_submission_results.sql` adds hash-only, expiring one-time administrator submission/result gates and stores no result or client-secret plaintext. Migrations `0006` and `0007` add and index internal file-repair state. Migration `0009_account_credential_purge.sql` indexes finite subject purge phases and adds nullable subject ownership for new revoked-JTI rows; legacy rows remain unattributed and are deliberately retained. Migration `0010_account_deletion_finalization.sql` adds in-flight R2 write fences, subject-retirement write triggers, and fail-closed clean-completion triggers. Migration `0011_audit_actor_attribution.sql` moves only canonical 43-character SHA-256 base64url legacy actor hashes from generic audit JSON into a nullable deterministically indexed column, removes malformed legacy fields without attribution, and deletes no events. Migration `0012_service_clients.sql` distinguishes non-human service principals and clients while retaining existing storage foreign keys; service/client creation is one D1 batch. Repair/fence state contains no logical filename, content, credential, secret, or error text and has no caller-facing route. Durable requests schedule at most 25 repair candidates per minute through `waitUntil`; referenced bytes are retained and transient failures remain queued. A healthy request path must never create or alter tables. After deployment, run D1 `PRAGMA foreign_key_check`, confirm all twelve migrations applied in order, and verify `/session`, current-session storage, and a disposable service client that obtains two distinct short-lived tokens for one isolated namespace. Rotate its secret, revoke/disable it, and remove test data after proof. A missing reserved browser-client or service-client migration causes those focused operations to fail closed instead of creating schema at request time.

`POST /account/deletion` is the authenticated request operation and content-negotiated `GET /account/deletion` is its coarse status resource; there is no deployment-wide deletion or special re-registration operation. POST requires the existing D1 and R2 bindings plus a request execution context capable of `waitUntil`; missing background dependencies fail before job creation. A first accepted request sets `aittadb_account_deletion_status` as a host-only `HttpOnly`, `Secure`, `SameSite=Lax` cookie with `Path=/account/deletion` and `Max-Age=604800`, then schedules one internal coordinator pass. The handle uses signing-key material but a distinct HKDF/AES-GCM purpose and binds the exact issuer, `JWT_KEY_ID`, trusted email, and encrypted old subject. Issuer, key-ID, or private-key rotation invalidates outstanding status handles immediately. GET decrypts before D1, never reconstructs the old subject through email lookup, and schedules exactly one caught coordinator pass only for a valid noncompleted job. Missing R2 or `waitUntil` returns a coarse no-store `503` after the valid exact job read and schedules nothing; completed status needs no background dependency and offers only Sites sign-out. Each coordinator invocation claims one job for at most five minutes and advances finite fence, credential, record, and file batches; finalization additionally clears at most 100 matching audit actor attributions per attempt before user removal, preserving the events, so completion may require repeated invocations. Do not delete or rewrite `account_deletion_jobs` tombstones: the retained former UUID is the documented sole durable subject-linkable pseudonymous idempotency/security exception that permanently rejects old credentials. Once clean completion removes the email index, ordinary identity resolution may create one new UUID and empty namespace for the same email without reading or changing the old tombstone. Unattributed audit events keep their bounded retention policy and hashed rate keys their five-minute policy. Monitor retryable jobs and repair backlog without logging subjects, emails, confirmation/status values, client IDs, logical/physical keys, credentials, or repair details. A foreign-owner object reference intentionally prevents finalization and requires private data-integrity investigation; never bypass the clean-finalization predicates. Source validation proves the route contract but is not evidence that a live Sites deployment has completed an end-to-end account deletion.

When a deletion remains retryable, inspect private Worker logs for `account-deletion.coordinator.failed`. Its only payload fields are the constant event name and one phase enum (`fences`, `credentials`, `records`, `files`, or `finalization`); `finalization` also covers retry scheduling and terminal reconciliation. Do not broaden this diagnostic with identifiers, request data, exception text, SQL, object keys, credentials, configuration, or secrets. No event is expected for a successful pass.

A clean nonterminal pass instead emits `account-deletion.coordinator.deferred` with only the first incomplete `credentials`, `records`, `files`, or `finalization` phase. This distinguishes bounded progress or a durable integrity hold from an exception without exposing counts or state details. Completed, no-job, and stale-claim passes emit no deferred event.

For a `credentials` failure, the accompanying `account-deletion.credentials.failed` event narrows the D1 operation to one fixed subphase: `job`, `authorization-codes`, `authorization-requests`, `device-grants`, `consents`, `refresh-tokens`, `refresh-families`, `access-revocations`, `admin-submissions`, or `remaining-check`. It carries no adapter error, SQL, count, identity, request, credential, configuration, or secret. Use only that enum to select the focused repository investigation.

The credential `remaining-check` uses one subject-bound `SELECT ... WHERE EXISTS` statement rather than a compound `UNION ALL` query. Retain the single-statement form when changing owned credential tables: it is the Sites D1-compatible contract proven by the disposable deployment.

Dynamic application responses are configured with one-year HSTS including subdomains when production uses an HTTPS issuer. Confirm this and the effective header policy for static assets on the deployed custom domain before release. Also verify exact-origin CORS with active and disabled clients, token CORS, encrypted cursor pagination, concurrent file conflict behavior, each storage ceiling, the write kill switch, rate-limit recovery, migration cleanup, and two-user/two-client isolation. For administration, complete create, refresh, enable, disable, confidential/service secret rotation, grant revocation, stale-result replay, and secret-disappearance checks with the allowlisted live Sites identity. Source tests do not replace those live checks and must not be described as live verification.
