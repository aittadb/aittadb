# Threat Model

Covered MVP threats:

- Forged ChatGPT Sites identity headers: production trusts these only inside the Sites runtime. Its app assembly always injects the sole Sites header adapter and exposes no mock-identity binding or environment switch; tests explicitly inject a provider defined only under `tests/`.
- Deployment outside the trusted Sites edge: self-hosting requires replacing the upstream identity adapter.
- Stolen device and user codes: device codes are high entropy, short user codes expire, and both are stored only as hashes. Migration `0004` scrubs legacy user-code display values. The standard Device Grant response still returns the user code and complete verification URI; consent reconstructs the display value only from the matching same-origin browser submission. Polling is rate limited, and the polling client must authenticate and match the client that created the grant. AittaDB emits no code in its audit data, but operators must still treat infrastructure request URLs containing `verification_uri_complete` as sensitive.
- Authorization-code interception and transaction replay: PKCE `S256`, exact redirect URI matching, short expiry, and affected-row-gated one-time authorization-request and code transitions are required. Remembered-consent continuation, explicit approval, and denial share the same pending-only transition; repeated or concurrent decisions have one winner, while losers fail locally with `invalid_request` and cannot redirect, return a code, or reflect client state.
- Redirect URI injection: redirect URIs must exactly match registered values and must not include fragments.
- CSRF and login CSRF: browser approval, denial, protocol-console, UserInfo, storage-console, and admin forms require same-origin submissions and a high-entropy double-submit CSRF cookie. The host-only, secure, `HttpOnly`, `SameSite=Lax` token remains stable during its bounded browser-session window so concurrent tabs cannot invalidate each other; malformed, missing, or mismatched tokens fail closed. The origin validator recognizes the configured public issuer behind Sites' internal dispatch URL, accepts a `null` origin only when browser fetch metadata says `same-origin`, and rejects arbitrary origins. Standards-defined API POST requests remain usable without the browser-only `ui=1` marker.
- Token replay and token-type confusion: access tokens are short-lived and revocable by `jti`; every bearer consumer requires a signed `token_use=access`, so an ID token cannot authorize UserInfo, introspection, storage, or any shared access-token verifier. UserInfo also requires `openid`; introspection returns active only for an access token whose audience is its authenticated confidential client and treats ID and refresh tokens as inactive.
- Refresh-token theft and reuse: refresh tokens are opaque, hashed, client-bound, rotated through affected-row-gated consumption, and reuse revokes the token family. Revocation handles omitted or incorrect hints without disclosing token state.
- JWT algorithm and claim confusion: validation accepts ES256 only, rejects unknown `kid` values, verifies the signature, and enforces exact issuer and audience, expiration, future issued-at limits, and not-before. Authorization Code ID tokens preserve their registered-client audience and OIDC nonce.
- Signing-key exposure: keys are generated locally and configured as hosted secrets.
- Email reassignment: downstream tokens use an immutable local UUID, but Sites documents no stable upstream subject and AittaDB still locates ordinary users and administrators by email. An address change can create a second identity; reassignment can inherit the prior local UUID, its namespaces, and administrator membership when that UUID is in `ADMIN_SUBJECTS`. This remains an accepted MVP risk requiring a future upstream/account-migration contract.
- Malicious OAuth clients: admin-controlled registration, exact redirects, scoped clients, exact allowed origins, disablement, and token-audience active-client checks are supported. UserInfo/storage actual CORS uses the active audience client. Token preflight requires some active client registration, while the actual request must match its submitted active client before a code, device grant, or refresh token is consumed.
- Polling and registration abuse: one-statement D1 counters protect authorization creation, device authorization/polling through the token endpoint, client authentication/token exchange, revocation, introspection, administration, and storage. Endpoint-family counters are per hashed client IP plus deployment-wide at ten times the per-IP limit; storage also limits the hashed local-user/client namespace. The table fails closed for new keys at 10,000 rows. Cleanup runs at most once per minute, deletes up to 500 rows per category, and retains one-minute counters for five minutes. `429` responses include `Retry-After`. These are operational controls, not proof against distributed abuse.
- Administrator takeover, control tampering, and mutation replay: administration requires a current trusted ChatGPT Sites session mapped to a canonical local UUID in `ADMIN_SUBJECTS`; no key header or unlock form can bypass or supplement that check. Non-admin representations expose no client data or controls, and same-origin plus CSRF checks protect mutations. HTML, hypermedia, and POST validation share one state/type-aware operation policy, so a caller cannot rotate a public-client secret or invoke an omitted enable/disable transition. D1 atomically claims each one-time submission hash before mutation. HTML then uses Post/Redirect/Get with an encrypted, subject-bound, expiring, `HttpOnly`, `SameSite=Strict` result cookie whose hash-gated result is consumed once, so refresh and replay do not repeat the operation or reveal a secret again. A generated secret is client-bound, never placed in a URL or durable plaintext storage, and persisted only as a hash. Mutation audits use bounded identity-source data and hashed actor/client references. Subject allowlisting cannot prevent reassignment while local subjects are still located by email, so operators must keep the list narrow and treat reassignment as a residual risk.
- Privacy-contact disclosure or configuration probing: `/privacy` treats configured controller/contact fields as deliberately public and escapes them for each representation. When required fields are absent, it may resolve only the first canonical `ADMIN_SUBJECTS` user and disclose only that user's last stored email and optional display name. It never returns UUIDs, the allowlist, alternate users, secrets, bindings, or configuration provenance; an unavailable or invalid fallback fails with a generic `503`. Operators must use a role address when publishing a personal administrator address would be inappropriate and must account for stale-address and email-reassignment risk.
- Inaccurate privacy notice or residency claim: every deployment operator controls its clients, purposes, configuration, and Hosted Data and must review the baseline notice before publication and after material changes. OpenAI hosts and processes Sites Hosted Data under the applicable Sites terms and DPA, but AittaDB makes no fixed residency claim. The core has no analytics or advertising cookies; adding either changes the notice and consent analysis.
- Accidental credential logging: audit logging redacts credential-like fields.
- Browser credential exposure: bearer values are accepted only in request headers or protected form bodies, never query strings or browser storage. Token results use no-store responses and display credentials only as the direct one-time result of the real exchange.
- Interactive API documentation compromise: Swagger UI is version-pinned, checked into same-origin static assets, verified against the lockfile package in CI, restricted by CSP, and configured without persistent authorization state or external CDNs.
- Swagger cross-origin credential disclosure: "Try it out" rewrites request targets to the origin serving the viewer and uses same-origin credentials, so a custom-domain viewer does not submit to a stale or legacy OpenAPI server URL.
- Forks retaining deployment identifiers or keys: reusable source must not publish real `project_id` or committed signing keys.
- Cross-user and cross-client storage access: every D1 read, list, write, and delete is keyed by both the immutable AittaDB user UUID and OAuth client ID. An access token for another user or client cannot observe, replace, or delete the owner's records or file metadata.
- Shared-storage exhaustion: every create or replacement uses one conditional D1 statement to enforce finite combined record/file item and byte ceilings for the deployment, local user, and local-user/client namespace. The operational write kill switch stops creates/replacements while allowing reads and deletes. These limits can be misconfigured and do not reveal or guarantee Sites capacity, which may be lower and remains numerically undocumented.
- Unbounded enumeration and usage inference: record and file collections have finite `page_size`, deterministic ordering, and AES-GCM cursors bound to kind, user, and client through additional authenticated data. Tokens expose no logical key, timestamp, namespace identifier, signing material, or secret. Private signing-key rotation immediately invalidates them; clients recover by restarting from the collection URI. Responses reveal only current-namespace usage and ceilings, never deployment or cross-client totals.
- Reserved browser-client impersonation: current-session UserInfo and storage use a migration-seeded internal client. It is hidden and non-administrable, and OAuth client authentication, device authorization/polling, and Authorization Code initiation reject its fixed ID. Its short-lived internal tokens are never returned to HTML, cookies, URLs, logs, or browser storage.
- Internal deployment-data probing: there is no generic D1, SQL, R2 listing, environment, binding, or secret endpoint. Storage responses omit local owner IDs, client IDs, physical object keys, signing material, and configuration values. JWKS publishes verification-only public key material.
- Public statistics inference: `/statistics` returns only one aggregate local-identity count. It exposes no rows, email addresses, display names, UUIDs, client relationships, storage totals, or filtering controls.
- R2 object-key injection: caller-provided storage keys are logical metadata only; physical R2 keys are generated by AittaDB.
- File-creation key injection: collection `POST /storage/files` generates the logical key server-side; item `PUT` accepts only its validated URL key. Both generate a separate physical R2 key and enforce the same user/client ownership boundary.
- Oversized request bodies: URL-encoded forms, JSON records, raw files, and browser multipart wrappers are consumed with streaming aggregate limits before complete buffering or parsing. JSON records and files retain 64 KiB and 10 MiB canonical limits.
- Multipart browser abuse: before reading multipart bytes, the same-origin file adapter requires trusted Sites identity, including explicit-token mode. It then stream-bounds the complete body, distrusts declared length, validates `File.size`, permits only documented operations, and passes bytes through the canonical 10 MiB limit. Raw bearer API uploads remain available without browser sign-in.
- Browser storage-token leakage: forms use POST bodies with no token query parameter, results omit submitted and internally issued tokens, and no cookie, local storage, session storage, or hidden follow-up form retains bearer values.
- Bucket misconfiguration: file endpoints fail closed when the `BUCKET` binding is unavailable.
- D1/R2 partial failure and concurrency: file metadata transitions compare the observed physical key in one D1 statement. Stale creates/replacements/deletes return `409`; losing new objects are retired, and rollback cannot overwrite a newer winner. Copy-on-write, presence checks, and bounded compensation keep metadata paired after isolated failures. D1 and R2 share no transaction, so persistent primary plus compensation failure can require operator repair; responses remain generic.
- Expired-state accumulation: durable routes schedule non-authoritative cleanup outside the response at most once per one-minute Worker instance interval. A run deletes at most 500 expired rows per category and uses indexed relationship checks. Empty refresh families are retained for a one-hour creation grace period. Audit events become eligible after 90 days and one-minute counters after five minutes. A backlog can require repeated traffic or operator cleanup; eligibility is not a guaranteed deletion instant and request handling never performs an unbounded sweep.
- Transport downgrade: dynamic application responses for a production HTTPS issuer include one-year HSTS with `includeSubDomains`; local HTTP development intentionally omits it. Static-asset and reverse-proxy behavior must be checked at the deployed edge so the effective HTTPS boundary is not assumed from source alone.
- Hypermedia action tampering: advertised actions are convenience controls, not authorization grants. Every followed HTML or JSON action revalidates identity, client, scopes, ownership, state, origin, CSRF where applicable, input, and size limits.

The mitigations above describe source and local test behavior. Each release candidate still requires live verification of the exact deployed commit for Sites header stripping, HSTS, exact-origin CORS, disabled clients, storage ceilings, pagination, rate recovery, cleanup behavior, the write kill switch, and production tenant isolation. A two-user/two-client exercise is required when two authenticated identities are available; platform-limited evidence must be recorded honestly rather than inferred from local tests.
