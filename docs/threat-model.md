# Threat Model

Covered MVP threats:

- Forged ChatGPT Sites identity headers: production trusts these only inside the Sites runtime. Its app assembly always injects the sole Sites header adapter and exposes no mock-identity binding or environment switch; tests explicitly inject a provider defined only under `tests/`.
- Deployment outside the trusted Sites edge: self-hosting requires replacing the upstream identity adapter.
- Stolen device and user codes: device codes are high entropy, short user codes expire, and both are stored only as hashes. Migration `0004` scrubs legacy user-code display values. The standard Device Grant response still returns the user code and complete verification URI; consent reconstructs the display value only from the matching same-origin browser submission. Polling is rate limited, and the polling client must authenticate and match the client that created the grant. AittaDB emits no code in its audit data, but operators must still treat infrastructure request URLs containing `verification_uri_complete` as sensitive.
- Authorization-code interception and transaction replay: PKCE `S256`, exact redirect URI matching, short expiry, and affected-row-gated one-time authorization-request and code transitions are required. Remembered-consent continuation, explicit approval, and denial share the same pending-only transition; repeated or concurrent decisions have one winner, while losers fail locally with `invalid_request` and cannot redirect, return a code, or reflect client state.
- Redirect URI injection: redirect URIs must exactly match registered values and must not include fragments.
- CSRF and login CSRF: browser approval, denial, protocol-console, UserInfo, storage, event-publication, administration, and account-deletion forms require same-origin submissions and a high-entropy double-submit CSRF cookie. A route-level pre-body classifier covers every enabled browser mutation adapter and rejects missing, malformed, foreign, same-site, cross-site, and unauthorized opaque origins before body pulls, rate-limit or repository writes, R2 access, or cleanup scheduling. It accepts the exact configured issuer behind Sites dispatch and permits `Origin: null` only with exact `Sec-Fetch-Site: same-origin`. The host-only, secure, `HttpOnly`, `SameSite=Lax` CSRF token remains stable during its bounded browser-session window, including ChatGPT sign-in return, so concurrent tabs cannot invalidate each other. Stale, missing, mismatched, and even matching-but-malformed cookie/form pairs fail closed after bounded parsing and before domain mutation; a fresh reload recovers without weakening validation. Origin classification and CSRF matching are independent mandatory controls. Machine OAuth requests and raw bearer storage uploads retain their protocol authentication and CORS behavior.
- Token replay and token-type confusion: access tokens are short-lived and revocable by `jti`; every bearer consumer requires a signed `token_use=access`, so an ID token cannot authorize UserInfo, introspection, storage, Events, or any shared access-token verifier. UserInfo also requires a human subject and `openid`; confidential/service introspection returns active only for an access token whose audience is the authenticated client and treats ID and refresh tokens as inactive.
- Refresh-token theft and reuse: refresh tokens are opaque, hashed, client-bound, rotated through affected-row-gated consumption, and reuse revokes the token family. Revocation handles omitted or incorrect hints without disclosing token state.
- JWT algorithm and claim confusion: validation accepts ES256 only, rejects unknown `kid` values, verifies the signature, and enforces exact issuer and audience, expiration, future issued-at limits, and not-before. Authorization Code ID tokens preserve their registered-client audience and OIDC nonce.
- Signing-key exposure: keys are generated locally and configured as hosted secrets.
- Email reassignment: downstream tokens use an immutable local UUID, but Sites documents no stable upstream subject and AittaDB still locates ordinary users and administrators by email. Before deletion, reassignment can inherit the prior local UUID, its namespaces, and administrator membership when that UUID is in `ADMIN_SUBJECTS`. After completed deletion, the same email creates a fresh UUID and empty namespace, but AittaDB cannot determine whether the holder is the same person. This remains an accepted MVP risk requiring a future upstream/account-migration contract.
- Concurrent local-user resolution and commit uncertainty: exact case-sensitive email resolution is one D1 upsert that inserts a generated UUID or updates and returns the canonical conflict row. It preserves the existing UUID, email, and creation time and changes only display name and update time. The repository rejects absent, malformed, multiple, or unsuccessful returned-row outcomes. If D1 commits but its response is lost, the failed request mints no usable alternate identity; retrying the same exact email returns the committed UUID. The test-only memory implementation performs lookup through insertion synchronously and preserves the same mapping semantics.
- Account-deletion authorization, handle replay, races, and disclosure: `POST /account/deletion` resolves the current trusted Sites identity through an exact-email read-only lookup and never creates or updates a user. A short-lived AES-GCM confirmation is purpose/issuer/subject/email-bound, while first acceptance creates a separate seven-day status handle under distinct HKDF/AES-GCM purposes. The status handle binds issuer, key ID/material, exact trusted email, and encrypted old subject, so tampering, expiry, signing-key or key-ID rotation, issuer mismatch, switched identity, and cross-purpose reuse fail before D1. Same-origin, CSRF, an exact human phrase, a 1 KiB form/JSON bound, pseudonymous per-IP/global counters, and the `ADMIN_SUBJECTS` denial precede atomic start. Only the first creation receives the scoped host-only status cookie, schedules one caught coordinator pass, and receives coarse no-store `202`; replay and an existing job are generic and unchanged. `GET /account/deletion` reads trusted identity and the cookie before repository availability, resolves no identity by email, and performs no D1/R2/cleanup/rate/coordinator work for a missing or cryptographically invalid handle. A valid handle permits only one exact old-subject job read. Noncompleted success schedules one caught bounded coordinator pass; completed and errors schedule none. Status output exposes only pending/running/retry/completed and one valid refresh/recovery action, with Sites sign-out as the sole completed transition; status never creates or identifies a replacement account. Migration `0008` stores one internal row keyed by immutable local subject; starts are idempotent and finite claims bind an incrementing attempt plus unexpired lease. One shared gate treats every row state as inactive for new sessions/credentials, refresh successors, and existing access-token consumers. Storage denial precedes namespace access or mutation, introspection reports inactive, and external errors do not identify deletion state. Migrations `0010` and `0013` reject late writes that would attach credentials, grants, storage, or application events to a retiring subject. The memory adapter applies the same write-boundary invariant. Request, acceptance, and status representations expose no subject, email, job, attempt, timestamp, count, client/namespace, storage, or credential value; audits and logs receive no confirmation, handle, or deletion detail. No deployment-wide deletion or special re-registration operation exists.
- Account-deletion convergence and finalization: one invocation claims at most one job and advances at most 25 expired fences, 100 credentials/grants (including administrator submissions), 100 records, 100 events, and 25 files. Each committed absence is durable retry progress; exact multiples need a final empty pass. The event phase requires the exact human subject's current unexpired attempt, so stale workers and service principals cannot delete events. Stale/expired attempts cannot retry or finalize, and concurrent coordinators cannot share one lease. Finalization conditionally deletes the user and marks the exact job completed in one D1 batch only after every subject-owned row, event, fence, and repair is absent. Completion triggers prevent alternate dirty terminal transitions. An uncertain D1 response is reconciled only by observing that clean terminal state. The email index and aggregate identity count then exclude the user. A later ordinary identity lookup may create exactly one new UUID for the same email, but it starts with no connection to the old tombstone, grants, credentials, consent, revocation attribution, administrator submissions, records, files, or events. Old refresh tokens cannot rotate and AittaDB rejects old access tokens immediately. Signature-only external verification may still accept old access and ID JWTs for the former subject until `exp`; they never identify the replacement subject. OAuth clients, service principals, anonymous pending flows, other subjects/namespaces, redacted audits, and bounded rate state remain isolated.
- Malicious OAuth clients and stolen service secrets: admin-controlled registration, exact interactive redirects/origins, scopes, disablement, secret rotation, revocation, and active-client audience checks are supported. Events scopes and routes are accepted and advertised only while their default-off feature is enabled; stale registrations, pending grants, and refresh state cannot issue them after disablement. They authorize only the caller's AittaDB namespace. Collection and item reads require `events.read`, an active token audience and subject, exact principal/client repository predicates, and exact audience-client CORS; bounded queries, encrypted filter-bound cursors, and generic item errors prevent cross-namespace probing. Long polling additionally requires `events.subscribe`, a valid namespace/filter-bound cursor, a separate admission counter, a finite deadline/read ceiling, and cancellation checks; foreign-namespace publications never satisfy its prepared query. Service clients have no redirects or origins, accept only enabled storage and Events scopes, receive no user claims, ID token, or renewable bearer credential, and use their UUID as a namespace isolated from humans and other clients. A stolen service secret can mint short-lived tokens until rotation or disablement, so it remains server-side and hash-only at rest. UserInfo/storage/Events CORS uses the active audience client. Token preflight requires an active interactive client origin, while the actual token request must match the client named by `client_id` or HTTP Basic before a code, device grant, or refresh token is consumed.
- Polling and registration abuse: one-statement D1 counters protect authorization creation, device authorization/polling through the token endpoint, client authentication/token exchange, revocation, introspection, administration, account-deletion requests, storage, event publication, and event subscription. Endpoint-family counters are per hashed client IP plus deployment-wide at ten times the per-IP limit; storage and Events also limit the hashed principal/client namespace. The table fails closed for new keys at 10,000 rows. Cleanup runs at most once per minute, deletes up to 500 rows per category, and retains one-minute counters for five minutes. `429` responses include `Retry-After`. These are operational controls, not proof against distributed abuse.
- Administrator takeover, control tampering, and mutation replay: administration requires a current trusted ChatGPT Sites session mapped to a canonical local UUID in `ADMIN_SUBJECTS`; no key header or unlock form can bypass or supplement that check. Non-admin representations expose no client data or controls, and same-origin plus CSRF checks protect mutations. HTML, hypermedia, and POST validation share one state/type-aware operation policy, so a caller cannot rotate a public-client secret or invoke an omitted enable/disable transition. D1 atomically claims each one-time submission hash before mutation. HTML then uses Post/Redirect/Get with an encrypted, subject-bound, expiring, `HttpOnly`, `SameSite=Strict` result cookie whose hash-gated result is consumed once, so refresh and replay do not repeat the operation or reveal a secret again. A generated secret is client-bound, never placed in a URL or durable plaintext storage, and persisted only as a hash. Mutation audits use bounded identity-source data and hashed actor/client references. Subject allowlisting cannot prevent reassignment while local subjects are still located by email, so operators must keep the list narrow and treat reassignment as a residual risk.
- Privacy-contact disclosure or configuration probing: `/privacy` treats configured controller/contact fields as deliberately public and escapes them for each representation. When required fields are absent, it may resolve only the first canonical `ADMIN_SUBJECTS` user and disclose only that user's last stored email and optional display name. It never returns UUIDs, the allowlist, alternate users, secrets, bindings, or configuration provenance; an unavailable or invalid fallback fails with a generic `503`. Operators must use a role address when publishing a personal administrator address would be inappropriate and must account for stale-address and email-reassignment risk.
- Inaccurate privacy notice or residency claim: every deployment operator controls its clients, purposes, configuration, and Hosted Data and must review the baseline notice before publication and after material changes. OpenAI hosts and processes Sites Hosted Data under the applicable Sites terms and DPA, but AittaDB makes no fixed residency claim. The core has no analytics or advertising cookies; adding either changes the notice and consent analysis.
- Accidental credential logging: audit logging redacts credential-like fields. Background cleanup catches its own rejection before `waitUntil` and emits only one fixed generic failure event. Optional success telemetry is default-off, private-logs-only, and projects the fixed report to bounded semantic categories, verified counts or `null`, and limits; extra repository fields, including event identity, type, payload, owner, client, and cursor, cannot reach it.
- Browser credential exposure: bearer values are accepted only in request headers or protected form bodies, never query strings or browser storage. Token results use no-store responses and display credentials only as the direct one-time result of the real exchange.
- Interactive API documentation compromise: Swagger UI is version-pinned, checked into same-origin static assets, verified against the lockfile package in CI, restricted by CSP, and configured without persistent authorization state or external CDNs.
- Swagger cross-origin credential disclosure: "Try it out" rewrites request targets to the origin serving the viewer and uses same-origin credentials, so a custom-domain viewer does not submit to a stale or legacy OpenAPI server URL.
- Forks retaining deployment identifiers or keys: reusable source must not publish real `project_id` or committed signing keys.
- Cross-user and cross-client storage access: every D1 read, list, write, and delete is keyed by both the immutable AittaDB user UUID and OAuth client ID. An access token for another user or client cannot observe, replace, or delete the owner's records or file metadata.
- Bounded-record races, replay, and disclosure: protocol 1.1 authenticates the active token namespace and exact scopes before record, receipt, precondition, or quota lookup. One D1 batch validates a consistent pre-state, applies at most 25 unique-key mutations, verifies their postconditions, and commits the hash-keyed receipt or rolls everything back. Exact retries return the original bounded result; changed operation-ID reuse conflicts. Fixed failures contain no key, value, operation ID, cursor, quota, principal, credential, SQL, path, or exception detail. Receipt ceilings prevent check-only idempotency traffic from becoming unbounded.
- Event-identifier probing: a public event UUID is not authority. The item handler requires `events.read`, an active subject and exact active audience client, then performs one prepared principal/client/UUID query. Malformed, absent, expired, cross-user, and cross-client IDs share one generic no-store `404`; output omits sequence, owner/client keys, request hashes, and idempotency state. The outer default-off gate, token/identifier bounds, exact CORS, and rate limit precede repository disclosure.
- Shared-storage exhaustion: every create or replacement uses one conditional D1 statement to enforce finite combined record/file item and byte ceilings for the deployment, local user, and local-user/client namespace. The operational write kill switch stops creates/replacements while allowing reads and deletes. These limits can be misconfigured and do not reveal or guarantee Sites capacity, which may be lower and remains numerically undocumented.
- Event-log exhaustion: one conditional D1 append enforces independent finite deployment, local-user, and user/client event item and exact UTF-8 payload-byte ceilings. A rejected append writes no row, an exact idempotent replay consumes no additional capacity, and reads plus bounded retention remain available. Quota outcomes expose no aggregate usage or other namespace state; operator limits remain AittaDB controls rather than Sites capacity claims.
- Unbounded enumeration and usage inference: record and file collections have finite `page_size`, deterministic ordering, and AES-GCM cursors bound to kind, user, and client through additional authenticated data. Tokens expose no logical key, timestamp, namespace identifier, signing material, or secret. Private signing-key rotation immediately invalidates them; clients recover by restarting from the collection URI. Responses reveal only current-namespace usage and ceilings, never deployment or cross-client totals.
- Reserved browser-client impersonation: current-session UserInfo, storage, and event-item reads use a migration-seeded internal client. It is hidden and non-administrable, and OAuth client authentication, device authorization/polling, and Authorization Code initiation reject its fixed ID. Its short-lived internal tokens are never returned to HTML, cookies, URLs, logs, or browser storage.
- Internal deployment-data probing: there is no generic D1, SQL, R2 listing, environment, binding, or secret endpoint. Storage responses omit local owner IDs, client IDs, physical object keys, signing material, and configuration values. JWKS publishes verification-only public key material.
- Public statistics inference: `/statistics` returns only one aggregate local-identity count. It exposes no rows, email addresses, display names, UUIDs, client relationships, storage totals, or filtering controls.
- R2 object-key injection: caller-provided storage keys are logical metadata only; physical R2 keys are generated by AittaDB.
- File-creation key injection: collection `POST /storage/files` generates the logical key server-side; item `PUT` accepts only its validated URL key. Both generate a separate physical R2 key and enforce the same user/client ownership boundary.
- Oversized request bodies: accepted URL-encoded forms, JSON records, and canonical raw files use one shared streaming limit before route-owned parsing or persistence. A valid oversized `Content-Length` fast-fails without a stream pull; absent, malformed, and undersized values cannot bypass the observed-byte limit. Overflow returns a generic documented `413`, a failed stream returns `400`, and neither reaches R2 or D1 resource metadata. Forms and records are prebuffered before CORS client lookup, rate limiting, authentication, or repository access; raw files are bounded after bearer authorization but before hashing or storage. Browser multipart wrappers have a separate aggregate limit. JSON records and files retain 64 KiB and 10 MiB canonical limits.
- Multipart browser abuse: before reading multipart bytes, the same-origin file adapter requires trusted Sites identity, including explicit-token mode. Anonymous and malformed-identity requests return before a stream pull, rate-counter or cleanup write, storage-repository call, or R2 access. Accepted requests then stream-bound the complete body, distrust declared length, validate `File.size`, permit only documented operations, and pass bytes through the canonical 10 MiB limit. Raw bearer API uploads remain available without browser sign-in.
- Browser storage-token leakage: forms use POST bodies with no token query parameter, results omit submitted and internally issued tokens, and no cookie, local storage, session storage, or hidden follow-up form retains bearer values.
- Bucket misconfiguration: file endpoints fail closed when the `BUCKET` binding is unavailable.
- D1/R2 partial failure and concurrency: file metadata transitions compare the observed physical key in one D1 statement. Before every R2 put, storage reserves a durable owner/client fence for a random `objects/<uuid>` key and sends no subject/client/logical-key custom metadata. A deletion can start while an earlier put is in flight, but the fence blocks finalization and no later metadata attachment can cross the D1 retirement trigger. Metadata failure deletes R2 before releasing the fence; failed retirement or expiry atomically creates/updates repair state before fence removal. Finalization counts even expired fences. A total D1 outage before reservation prevents R2 mutation; after reservation, the durable fence/repair path remains the convergence record.
- Account file purge abuse or partial failure: the internal purge rejects a missing deletion job, stale claim, wrong attempt, or expired lease before D1/R2 mutation. A transactional D1 batch stages no more than 25 exact subject-owned metadata rows into repair before deleting them. Classification checks all metadata references: a foreign-owner reference is a conflict, remains deferred, preserves bytes, and blocks target finalization. Unreferenced R2 deletion and repair completion are idempotent. Progress/errors contain no subject, client, logical/physical key, content, credential, or repair detail. A completed tombstone authorizes only a clean no-op.
- Account event purge abuse or partial failure: one prepared delete requires the exact running attempt, unexpired lease, and a live human principal before removing at most 100 exact-subject events in deterministic order. Service-principal and unrelated-subject events are outside the statement. Statement failure rolls back its batch; earlier committed batches are the resume marker. Event append fails after deletion starts, and runtime plus migration finalization guards require zero owned events before completion. Coordinator telemetry exposes only the fixed `events` phase, never event identity, type, payload, owner, client, cursor, SQL, or exception.
- Deletion tombstone and bounded pseudonymous retention: finalization removes email, display name, the local user, and all attributed content/credential state. It clears at most 100 deterministically ordered matching audit actor hashes per exact live attempt before user removal, preserving audit events and unrelated attribution; partial and uncertain batches retry safely. It deliberately retains the former raw local UUID with coarse job state/attempt/timestamps as the linkable permanent security/idempotency exception. SHA-256 storage-rate owner keys remain under the five-minute counter policy and are not enriched during deletion.
- Expired-state accumulation: durable routes schedule non-authoritative cleanup outside the response at most once per one-minute Worker instance interval. A run deletes at most 500 expired rows per category, including application events and admin submissions, and 25 expired file-write fences. Events use indexed expiry/sequence ordering; other categories use the oldest eligibility timestamp and a deterministic tie-breaker. Empty refresh families are retained for a one-hour creation grace period. Audit events become eligible after 90 days and one-minute counters after five minutes. Missing or malformed D1 mutation counts remain unverifiable; they are never reported as zero. A backlog can require repeated traffic or operator cleanup; eligibility is not a guaranteed deletion instant and request handling never performs an unbounded sweep.
- Transport downgrade: dynamic application responses for a production HTTPS issuer include one-year HSTS with `includeSubDomains`; local HTTP development intentionally omits it. Static-asset and reverse-proxy behavior must be checked at the deployed edge so the effective HTTPS boundary is not assumed from source alone.
- Hypermedia action tampering: advertised actions are convenience controls, not authorization grants. Every followed HTML or JSON action revalidates identity, client, scopes, ownership, state, origin, CSRF where applicable, input, and size limits.

The mitigations above describe source and local test behavior. Each release candidate still requires live verification of the exact deployed commit for Sites header stripping, HSTS, exact-origin CORS, disabled clients, storage ceilings, pagination, rate recovery, cleanup behavior, the write kill switch, and production tenant isolation. A two-user/two-client exercise is required when two authenticated identities are available; platform-limited evidence must be recorded honestly rather than inferred from local tests.
