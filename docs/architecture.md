# Architecture

AittaDB runs as a Sites-compatible Vinext project with a Cloudflare Worker-compatible Fetch router in `src/handler.ts`. Vinext remains the build wrapper; API endpoints are protocol-first Fetch handlers.

System units:

- `src/identity.ts`: `UpstreamIdentityProvider` contract and the sole production ChatGPT Sites header adapter.
- `src/config.ts`: strict environment parsing, secure defaults, and the typed deployment feature-availability contract.
- `src/oauth.ts`: OAuth/OIDC domain behavior.
- `src/crypto.ts`: Web Crypto random values, hashes, PKCE, ES256 JWTs, and JWKS.
- `src/store/d1.ts`: D1 repository implementation.
- `src/store/memory.ts`: test-only repository implementation.
- `src/system-client.ts`: immutable reserved browser-client contract and external-flow guard.
- `src/browser-session.ts`: current Sites identity to minimal short-lived internal access-token adapter.
- `src/storage.ts`: AittaDB application-storage endpoints and scope enforcement.
- `src/storage-cursor.ts`: encrypted collection cursors bound to storage kind, local user, and OAuth client.
- `src/storage-browser.ts`: CSRF-protected HTML adapter that forwards browser record/file operations into `src/storage.ts`.
- `src/storage-pages.ts`: focused browser forms and readable storage results with no credential persistence.
- `src/hypermedia.ts`: versioned resource documents, semantic links, actions, fields, and representation negotiation.
- `src/admin-clients.ts`: one state/type-aware OAuth-client operation policy shared by HTML, hypermedia, and mutation validation.
- `src/admin-result.ts`: one-time admin submission state and encrypted, subject-bound HTML mutation results.
- `src/transaction-resources.ts`: representation-independent Device Grant and consent resources.
- `src/handler.ts`: HTTP route handling, representation negotiation, CORS, CSRF, and browser flows backed by production services.
- `src/openapi.ts`: canonical OpenAPI source served by `/openapi.json`.
- `tests/helpers.ts`: explicit mock identity provider and other test-only adapters; it is not imported by deployed modules.

The service stores structured application state in D1. JSON storage records are D1 rows keyed by AittaDB user UUID, OAuth client ID, and logical app key. File metadata is stored in D1 while file bytes are stored in R2 through binding `BUCKET`; physical R2 keys are generated by AittaDB and are not caller-controlled.

Feature availability is configured only through strict server-side booleans. Records, Files, and Statistics default on; downstream OAuth Apps default off. Malformed values fail configuration loading. The effective state is published as four booleans in HTML and versioned hypermedia service metadata so clients can distinguish deployment policy from missing routes without learning environment values or secrets. Records and Files gates are evaluated independently at the outer request boundary, before CORS client lookup, authentication, rate limiting, body parsing, cleanup scheduling, D1 storage work, or R2 access. The OAuth Apps gate likewise rejects client administration, Authorization Code and Device Grant initiation, their browser continuations, and `/oauth/token` before body reading, identity, CORS client lookup, rate limiting, client authentication, credential lookup or consumption, cleanup, or durable work; service metadata omits those controls. Token POST uses a no-store OAuth `temporarily_unavailable` response, while application resources use content-negotiated `feature_unavailable`. The reserved current-session client remains private and usable only by AittaDB's signed-in-session adapter. Other feature families retain their existing behavior.

Storage writes use one conditional D1 statement to enforce combined record-and-file item and byte ceilings at three levels: the deployment, one local user across clients, and one local-user/client namespace. The finite defaults are independent AittaDB controls rather than claims about Sites capacity. The write kill switch prevents record/file create and replace operations but leaves authorized reads and deletes available. Responses disclose only the current namespace's usage and namespace ceiling, never the deployment or per-user aggregates used for enforcement.

Collection reads use deterministic `updated_at DESC, key ASC` ordering and fetch at most `page_size + 1` rows to determine whether a next page exists. The response returns at most the bounded page size and, when needed, a canonical AES-256-GCM cursor whose key is domain-separated and derived from the private signing-key material. Authenticated-encryption additional data binds storage kind, local user, and OAuth client without serializing those identifiers into the token; the ciphertext exposes no logical key, timestamp, namespace identifier, signing material, or secret. No authoritative cursor state or previous cursor key is stored. Rotating the private signing-key material immediately invalidates outstanding cursors, and clients restart traversal from the collection URI.

D1 access is implemented with narrow repositories and prepared SQL statements. The project does not use Drizzle ORM or Drizzle Kit: reviewed SQL lives in `db/migrations/`, the required-table manifest lives in `db/schema.ts`, and `build/sites-migrations.ts` packages the reviewed statements plus the Sites migration journal into `dist/.openai/drizzle/`. `npm run db:check` prevents the manifest, migration history, and packaged ordering from silently diverging. Sites applies the deployment artifact migrations; request handlers never issue schema DDL.

It never stores or forwards ChatGPT credentials. Downstream `sub` values are locally generated immutable UUIDs.

Application assembly injects an `UpstreamIdentityProvider` through every identity-aware route. The deployed `createAittaDB` entry point always selects the Sites adapter, which reads only documented request headers. No runtime binding or environment mode can select a mock identity. Integration tests call `createAittaDBWithStore` with a provider defined under `tests/`, keeping synthetic users outside the Worker dependency graph.

Application URIs identify resources, not presentation-specific route trees. `Accept: text/html` selects semantic HTML; `Accept: application/vnd.aittadb+json; version=0.1` selects the versioned hypermedia representation; `application/json` is the compatibility representation. JSON documents contain `data`, semantic `links`, and currently authorized `actions`. HTML renders the same state and transitions as links, forms, lists, tables, and readable outcomes. Both representations call the same authorization, validation, domain, and repository units; representation selection never depends on `User-Agent`.

Application negotiation parses media-range quality, specificity, exclusions, wildcards, quoted parameters, and the preview version. No acceptable application representation returns `406`; vendor errors retain the vendor media type. Standards-defined OAuth/OIDC responses and file-byte delivery keep their protocol or binary media types instead of being wrapped.

The public root advertises real service operations in both representations. Its sign-in or sign-out action reflects the trusted server-side ChatGPT Sites identity signal. `/session` is the protected upstream-authentication boundary: it creates or retrieves the D1-backed local user and returns that same identity as HTML or JSON. When enabled, `/statistics` performs one prepared aggregate count and exposes only `identity_count`; it cannot enumerate identities or reveal personal fields. When disabled, the root omits its HTML and hypermedia controls and the route returns the same content-negotiated `503 feature_unavailable` contract before checking D1 availability, querying identities, or scheduling cleanup. Browser representations never maintain a second user, grant, token, or storage model.

`GET /privacy` is one public resource with accessible HTML and versioned hypermedia JSON representations. Explicit `PRIVACY_CONTROLLER_*` and `PRIVACY_CONTACT_*` values take precedence. If required controller/contact data is missing, the handler resolves only the first canonical UUID in `ADMIN_SUBJECTS` through the user repository and may publish that user's stored email and optional display name; it never emits the UUID, allowlist, or other user/configuration fields. If neither source yields a usable controller and contact, both representations fail generically with `503`. The baseline content and retention disclosures are maintained in `docs/privacy.md`.

Storage browser representations are resource-oriented. A collection `GET` renders a list or explicit empty state and item-navigation controls. `GET /storage/files` also renders a native file input; same-origin JavaScript may add accessible drag-and-drop feedback, but never changes the operation or security boundary. `POST /storage/files` creates a file under a server-generated logical key and returns `201 Created` plus an item `Location`. An item `GET` renders read/download, `PUT` create-or-update, and `DELETE` controls valid for only that URL key. Protected browser actions post to that same collection or item URL with a fixed method override. The adapter validates same-origin and CSRF state, rejects method/resource mismatches, derives item keys only from URLs, and invokes `storageEndpoint` through a synthetic `Authorization` header.

In current-session mode, the adapter maps the trusted Sites identity to the local user and issues a minimal short-lived credential for the reserved `aittadb-browser-session-v1` client. In token mode, it uses the explicitly submitted AittaDB token. The reserved client is migration-seeded, hidden from client lists, immutable through administration, and rejected by every external OAuth entry point. Its user/client ownership keys keep the durable signed-in AittaDB namespace separate from every third-party application, including applications used by the same user. `/auth-ui.js` only hides inactive form controls and upgrades collection navigation to the canonical item action; server-side validation and the no-JavaScript path remain complete.

All browser forms use a double-submit CSRF token in a host-only, secure, `HttpOnly`, `SameSite=Lax` cookie. A valid token is reused while its 15-minute cookie is active, including across ChatGPT sign-in return, so forms opened in concurrent tabs do not invalidate each other. Rendering replaces malformed cookie values with fresh high-entropy tokens. One pre-body route classifier covers every enabled HTML mutation adapter: protocol forms selected by `Accept: text/html`, browser-only session/device/consent/admin routes, and form-encoded or multipart storage adapters. It rejects an invalid origin before body pulls, rate counters, repository or R2 calls, and maintenance scheduling. The shared origin policy accepts an exact configured issuer origin even when Sites exposes an internal dispatch URL. It accepts opaque `Origin: null` only when `Sec-Fetch-Site` is exactly `same-origin`; missing, malformed, foreign, same-site, and cross-site signals fail closed. A valid origin then permits bounded form parsing and the independent canonical cookie/form CSRF comparison. CSRF failures still occur before domain mutation, and reloading renders a usable retry form. `/session` and `/privacy` remain GET-only; their current representations expose no local mutation form. Standards-defined machine OAuth requests and raw bearer storage uploads do not enter this browser-form classifier.

URL-encoded forms, record JSON, and raw file bodies use the shared stream-bound reader before buffering. Browser multipart upload wrappers additionally require trusted Sites identity before parsing, including explicit-token mode; an absent or malformed identity returns before pulling the stream, durable rate limiting or cleanup, storage-repository work, or R2 access. Raw bearer file APIs remain independent of browser sign-in. Record JSON reaches the same 64 KiB parser and D1 repository as REST `PUT`; file bytes reach the same 10 MiB canonical `POST`/`PUT` path even when `Content-Length` is absent, malformed, or untrustworthy. Raw overflow returns `413`; a failed raw stream returns `400`; neither reaches R2 or D1 file metadata. File replacement is copy-on-write, and each metadata create, replace, delete, or rollback uses D1 compare-and-set against the observed physical key. A stale writer returns `409` without overwriting a winner; its uncommitted R2 object is deleted or durably queued for private orphan repair when immediate retirement fails. Isolated D1 or R2 failures trigger bounded cleanup or rollback.

D1 and R2 have no shared transaction. When a file mutation and its bounded compensation cannot resolve a physical object, the storage domain records an internal delete-if-unreferenced candidate through `AuthStore.recordStorageFileOrphanRepair`. Migration `0006_storage_file_orphan_repairs.sql` stores only the generated R2 key, owning local-user/client namespace, and first/last activity timestamps. The physical key uniquely deduplicates repeated recording; a conflicting namespace cannot reassign an existing row. The table intentionally has no user/client foreign key so a repair remains durable across later account or client lifecycle work. It stores no logical key, content metadata, digest, error text, credential, or secret and has no HTTP, hypermedia, or OpenAPI surface.

The repair row is also an exclusion lock: every file-metadata upsert refuses its physical key while the row exists. Once-per-minute durable-route maintenance lists at most 25 rows in deterministic `updated_at`, `created_at`, and physical-key order. One D1 statement classifies each candidate as missing, globally referenced, or orphaned using the physical-key index. Missing candidates are skipped; referenced candidates retire only their queue row and preserve R2; only an explicit orphan classification reaches R2 deletion. The still-present row prevents reattachment until deletion and owner-bound completion. A failed R2 or D1 step leaves or re-touches the row, rotating it behind older work and allowing an idempotent later retry. Concurrent processors may repeat an orphan deletion but cannot reinterpret a removed referenced row as deletable. Migration `0007_storage_file_orphan_repair_order.sql` indexes the global reference check and finite fair ordering. The processor returns only aggregate internal counts and has no caller-visible route.

Authorization-request decisions, authorization-code consumption, approved-device consumption, and refresh-token consumption are conditional D1 updates whose affected-row count gates success. The remembered-consent `GET` continuation and explicit approval or denial `POST` all use the same pending-only authorization-request transition. A repeated or concurrent loser receives a local `invalid_request` response without a client redirect, callback URI, authorization code, or preserved state. Device polling updates only polling metadata and cannot restore a stale terminal status. Device and short user codes are persisted only as hashes; the short display code returned by RFC 8628 is reconstructed for consent from the matching same-origin browser submission, and migration `0004` blanks legacy display values. JWT validation accepts only ES256 and the configured `kid`, verifies the signature, and enforces exact issuer and audience plus expiration, issued-at, and not-before boundaries. Authorization Code ID tokens retain the registered client ID as audience and the original OIDC nonce. Every access-token consumer requires `token_use=access`; UserInfo additionally requires `openid` and an existing active audience client, while confidential-client introspection reports active only for a valid access token issued to that same client. Revocation authenticates the owning client, revokes an opaque refresh token's family, or records a verified access-token `jti`, with standards-compatible success non-disclosure and hint fallback.

Administrator access resolves the current trusted Sites identity to its AittaDB local user and requires that canonical UUIDv4 in `ADMIN_SUBJECTS`. There is no caller-supplied administrator key or unlock route. Same-origin and CSRF checks independently protect every mutation, and only allowlisted representations contain client data or administrative actions. HTML forms, versioned hypermedia actions, and POST validation use one operation policy: active clients can be disabled, disabled clients can be enabled, confidential clients can rotate secrets, and every listed client can revoke grants. An operation omitted for the current state or type is also rejected server-side. Each mutation atomically claims the submitted one-time token hash in D1 before changing client state. JSON returns the immediate no-store result. HTML uses Post/Redirect/Get; a five-minute encrypted, `HttpOnly`, `SameSite=Strict` cookie carries the result to one atomically gated GET, preventing refresh or replay from repeating the mutation or redisplaying a secret. The cookie contains no URL-visible plaintext, D1 stores no result or secret, and only the client-secret SHA-256 hash remains after consumption. Client-mutation audit records contain bounded event names, a fixed subject-authorization source, and hashed actor/client references; repository redaction still removes credential-like fields before persistence. Subject allowlisting does not remove email-reassignment risk because the user repository still locates that UUID by upstream email.

The self-hosted Swagger UI reads the canonical OpenAPI document, but its request interceptor targets the origin that serves the viewer. This keeps "Try it out" same-origin on custom domains and avoids sending credentials to a stale or legacy server URL.

Public metadata, health, discovery, JWKS, OpenAPI, documentation, and stylesheet requests do no D1 work. Enabled `/statistics` is a deliberate exception and executes only its bounded aggregate query; disabled `/statistics` does no store work. `/privacy` performs at most one user lookup only when explicit public contact configuration is insufficient. Static assets pass directly to Vinext. Durable routes schedule cleanup through `waitUntil` at most once per one-minute Worker instance interval. Each run deletes at most 500 rows per OAuth, device, refresh, revocation, admin-submission, audit, or rate category, selecting the oldest eligibility timestamp first and using `rowid` as a deterministic tie-breaker; covering relationship indexes support the request/code and family/token checks. Empty refresh families receive a one-hour grace period so cleanup cannot race first-token creation. Audit events become cleanup-eligible after 90 days and one-minute counters after five minutes. Atomic counters apply per-IP/global endpoint limits and per-user/client storage limits; new keys fail closed at 10,000 rows, and a global endpoint ceiling is ten times its per-IP ceiling.

For cross-origin UserInfo and storage calls, preflight origins must belong to an active registered client and an actual bearer request must match an exact origin on its own active audience client. Token preflight uses the active-client origin index; the actual token request must match the client named by `client_id` or HTTP Basic before a code, device grant, or refresh token is consumed. Other controlled routes use the configured exact origin list; no credentialed wildcard is used. Dynamic responses receive one-year `includeSubDomains` HSTS for a production HTTPS issuer. These controls and scheduling hints do not make process memory authoritative. Persistent Events remains planned and has no runtime or persistence contract in the MVP.
