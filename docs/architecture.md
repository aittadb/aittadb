# Architecture

AittaDB runs as a Sites-compatible Vinext project with a Cloudflare Worker-compatible Fetch router in `src/handler.ts`. Vinext remains the build wrapper; API endpoints are protocol-first Fetch handlers.

System units:

- `src/identity.ts`: trusted ChatGPT Sites header parsing and test-only identity adapter.
- `src/oauth.ts`: OAuth/OIDC domain behavior.
- `src/crypto.ts`: Web Crypto random values, hashes, PKCE, ES256 JWTs, and JWKS.
- `src/store/d1.ts`: D1 repository implementation.
- `src/store/memory.ts`: test-only repository implementation.
- `src/system-client.ts`: immutable reserved browser-client contract and external-flow guard.
- `src/browser-session.ts`: current Sites identity to minimal short-lived internal access-token adapter.
- `src/storage.ts`: AittaDB application-storage endpoints and scope enforcement.
- `src/storage-browser.ts`: CSRF-protected HTML adapter that forwards browser record/file operations into `src/storage.ts`.
- `src/storage-pages.ts`: focused browser forms and readable storage results with no credential persistence.
- `src/handler.ts`: HTTP route handling, representation negotiation, CORS, CSRF, and browser flows backed by production services.
- `src/openapi.ts`: canonical OpenAPI source served by `/openapi.json`.

The service stores structured application state in D1. JSON storage records are D1 rows keyed by AittaDB user UUID, OAuth client ID, and logical app key. File metadata is stored in D1 while file bytes are stored in R2 through binding `BUCKET`; physical R2 keys are generated by AittaDB and are not caller-controlled.

D1 access is implemented with narrow repositories and prepared SQL statements. The project does not use Drizzle ORM or Drizzle Kit: reviewed SQL lives in `db/migrations/`, the required-table manifest lives in `db/schema.ts`, and `build/sites-migrations.ts` packages the reviewed statements plus the Sites migration journal into `dist/.openai/drizzle/`. `npm run db:check` prevents the manifest, migration history, and packaged ordering from silently diverging. Sites applies the deployment artifact migrations; request handlers never issue schema DDL.

It never stores or forwards ChatGPT credentials. Downstream `sub` values are locally generated immutable UUIDs.

The public root advertises the real service operations in HTML and JSON hypermedia. `/session` is the protected upstream-authentication boundary: it reads the server-side ChatGPT Sites identity, creates or retrieves the D1-backed local user, and returns that same local identity as HTML or JSON. Browser representations never maintain a second user, grant, token, or storage model.

Storage browser forms post only to the collection routes. The adapter validates same-origin and CSRF state and invokes `storageEndpoint` through a synthetic `Authorization` header. In current-session mode, it maps the trusted Sites identity to the local user and issues a minimal short-lived credential for the reserved `aittadb-browser-session-v1` client. In token mode, it uses the explicitly submitted AittaDB token. The reserved client is migration-seeded, hidden from client lists, immutable through administration, and rejected by every external OAuth entry point. Its user/client ownership keys keep browser-session data separate from every third-party application, including applications used by the same user.

All browser forms use a double-submit CSRF token in a host-only, secure, `HttpOnly`, `SameSite=Lax` cookie. A valid token is reused while its 15-minute cookie is active so forms opened in concurrent tabs do not invalidate each other. Rendering rejects malformed cookie values and replaces them with fresh high-entropy tokens; submission still requires an exact token match and the independent same-origin check.

Record JSON reaches the same 64 KiB parser and D1 repository as REST `PUT`; multipart file bytes reach the same 10 MiB limit, generated physical key, D1 metadata write, and R2 object operation as REST `PUT`. Results omit all submitted or internal tokens and physical R2 keys.

Public metadata, health, discovery, JWKS, OpenAPI, documentation, and stylesheet requests do no D1 work. Static asset requests pass directly to Vinext. Durable-state routes schedule bounded expiration cleanup at most once per five-minute Worker instance interval through `waitUntil`, and OAuth-client relation hydration runs independent queries concurrently. These are latency optimizations only; no authoritative state depends on process memory or cleanup timing.
