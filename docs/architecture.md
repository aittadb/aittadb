# Architecture

AittaDB runs as a Sites-compatible Vinext project with a Cloudflare Worker-compatible Fetch router in `src/handler.ts`. Vinext remains the build wrapper; API endpoints are protocol-first Fetch handlers.

System units:

- `src/identity.ts`: `UpstreamIdentityProvider` contract and the sole production ChatGPT Sites header adapter.
- `src/config.ts`: strict environment parsing, secure defaults, and the typed deployment feature-availability contract.
- `src/oauth.ts`: OAuth/OIDC domain behavior.
- `src/crypto.ts`: Web Crypto random values, hashes, PKCE, ES256 JWTs, and JWKS.
- `src/store/d1.ts`: D1 repository implementation.
- `src/store/memory.ts`: test-only repository implementation.
- `src/store/account-deletion.ts`: finite account-deletion claim bounds and validation shared by both repositories.
- `src/store/account-credential-purge.ts`: credential/grant purge bounds and generic unavailability failure shared by both repositories.
- `src/store/account-record-purge.ts`: record-purge input bounds and non-sensitive batch progress shared by both repositories.
- `src/store/account-event-purge.ts`: lease-bound event-purge bounds and aggregate progress shared by both repositories.
- `src/account-file-purge.ts`: bounded internal account file purge and aggregate progress contract.
- `src/subject-access.ts`: protocol-independent active-subject authorization and administrator-safe deletion start.
- `src/system-client.ts`: immutable reserved browser-client contract and external-flow guard.
- `src/browser-session.ts`: current Sites identity to minimal short-lived internal access-token adapter.
- `src/storage.ts`: AittaDB application-storage endpoints and scope enforcement.
- `src/storage-cursor.ts`: encrypted collection cursors bound to storage kind, local user, and OAuth client.
- `src/bounded-record-protocol.ts`: strict vendor-neutral bounded record-storage protocol 1.1 documents, limits, and command decoding.
- `src/bounded-record-http.ts`: content-negotiated discovery, scoped reads/pages, and atomic transaction transport.
- `src/bounded-record-cursor.ts`: protocol-specific encrypted list position bound to principal, client, collection, and page size.
- `src/event-collection.ts`: bounded event collection reads, cursor traversal, and namespace authorization.
- `src/events.ts`: immutable event item representation and scoped `events.read` authorization.
- `src/event-pages.ts`: accessible HTML rendering of the same immutable event resource.
- `src/application-event-cursor.ts`: expiring encrypted Events checkpoints bound to one principal and OAuth client.
- `src/event-publication.ts`: bounded bearer and current-session adapters for one immutable event append.
- `src/storage-browser.ts`: CSRF-protected HTML adapter that forwards browser record/file operations into `src/storage.ts`.
- `src/storage-pages.ts`: focused browser forms and readable storage results with no credential persistence.
- `src/hypermedia.ts`: versioned resource documents, semantic links, actions, fields, and representation negotiation.
- `src/admin-clients.ts`: one state/type-aware OAuth-client operation policy shared by HTML, hypermedia, and mutation validation.
- `src/admin-result.ts`: one-time admin submission state and encrypted, subject-bound HTML mutation results.
- `src/transaction-resources.ts`: representation-independent Device Grant and consent resources.
- `src/handler.ts`: HTTP route handling, representation negotiation, CORS, CSRF, and browser flows backed by production services.
- `src/openapi.ts`: canonical OpenAPI source served by `/openapi.json`.
- `tests/helpers.ts`: explicit mock identity provider and other test-only adapters; it is not imported by deployed modules.

The service stores structured application state in D1. The legacy JSON API keeps flat logical keys in `storage_records`. Bounded record-storage protocol 1.1 uses the separate `bounded_storage_records` table keyed by principal UUID, OAuth client UUID, collection, and stable record ID, with exact UTF-8 byte count and a positive revision. Hash-keyed `bounded_storage_transaction_receipts` retain only the bounded ordered result and metadata required to replay one committed namespace operation; no public repository method lists or reads receipts. The separate tables preserve the legacy contract while giving the protocol deterministic collection ordering, compare-and-set state, and restart-safe idempotency. Human principals use a locally generated user UUID. A service client uses its own client UUID as both its non-human principal and client key, producing one stable namespace that cannot overlap a human or another client. File metadata is stored in D1 while file bytes are stored in R2 through binding `BUCKET`; physical R2 keys are generated by AittaDB and are not caller-controlled.

Feature availability is configured only through strict server-side booleans. Records, Files, and Statistics default on; downstream OAuth Apps and Events default off. Missing values use those defaults, while empty or malformed values fail configuration loading. The effective state is published as five booleans in HTML and versioned hypermedia service metadata without exposing environment values. Records and Files gates are evaluated independently at the outer request boundary before durable work. The OAuth Apps gate similarly rejects administration, grants, continuations, token, revocation, introspection, and UserInfo before parsing or state access. The Events flag enables its AittaDB-only scopes, atomic `POST /events`, bounded `GET /events`, and immutable `GET /events/{id}` for exact bearer or current-session namespaces. Disabled deployments reject stale scopes and the whole route family before origin/CORS, body, bearer, identity, rate, cursor, repository, or maintenance work and omit every Events control. Disabled issuer metadata retains only the public verification contract. OAuth POSTs use protocol errors; application resources use content-negotiated `feature_unavailable`. The reserved current-session client remains private and usable only by AittaDB's signed-in-session adapter.

Storage writes enforce combined legacy-record, bounded-record, and file item/byte ceilings at three levels: the deployment, one local user across clients, and one local-user/client namespace. Bounded transactions evaluate those ceilings against their complete post-transaction candidate state, so a delete may fund a put in the same commit. Durable transaction receipts have separate count/byte admission at the same three levels using the configured finite storage values; they neither consume nor appear in application-record usage. The finite defaults are independent AittaDB controls rather than claims about Sites capacity. Existing record and file upserts include bounded-record usage in their conditional D1 admission statements, so the new table cannot bypass an older namespace's limits. Before a file upload reaches R2 it reserves a durable owner/client write fence for an opaque `objects/<uuid>` key; R2 custom metadata contains no owner, client, or logical key. Metadata success or successful compensation releases the fence. Failed compensation and fence expiry atomically establish owner-bound TASK-119 repair state before clearing it. A quota loser commits no metadata, and repair retries remain finite. Responses disclose neither receipts, fences, repairs, nor physical keys. The write kill switch prevents record/file create and replace operations but leaves authorized reads and deletes available. Responses disclose only the current namespace's usage and namespace ceiling, never the deployment or per-user aggregates used for enforcement.

Event publication accepts one bounded typed JSON object through bearer JSON or a same-origin CSRF-protected current-session form. The verified access token is the sole source of principal/client ownership; the browser adapter mints but never exposes its minimal internal token. Before append, the adapter enforces media-specific stream limits, exact input fields, event type/data bounds, active subject/client and token purpose, `events.publish`, exact-origin CORS for browser bearer calls, and finite IP/global plus hashed namespace rate counters. It generates the UUID and expiry and performs no fan-out. Event append then uses independent finite deployment, local-user, and user/client item and exact UTF-8 payload-byte ceilings in the same conditional D1 insert that creates the immutable row. A namespace-bound hash-only idempotency key resolves an exact replay after a losing insert without a second allocation; conflicting content remains distinct from quota rejection. The memory transition does not yield between replay, quota, and insert decisions. Responses reveal no internal sequence, namespace key, stored hash, aggregate usage, or credential.

The immutable event-item handler authenticates a short-lived access token and resolves its active human or service principal plus exact active audience client before one prepared principal/client/UUID lookup. Current-session HTML and hypermedia requests mint an unexposed token for the reserved browser client and call that same handler. Canonical UUID validation precedes D1, and malformed, absent, expired, cross-user, and cross-client identifiers collapse to one no-store `404`. The representation excludes internal sequence, ownership, idempotency, and request-hash fields and offers only self and collection navigation.

Legacy collection reads retain deterministic `updated_at DESC, key ASC` ordering. Bounded record-storage pages instead read one exact collection in stable record-ID ascending order, fetch at most `page_size + 1`, and return at most 100 records. Their independent AES-256-GCM cursor contains only the last ID; domain-separated key derivation and authenticated data bind protocol kind, local subject, OAuth client, collection, and page size without serializing those values. A cursor is at most 2,048 characters and fails generically on tampering or binding mismatch. Neither collection stores authoritative cursor state or previous cursor keys. Rotating the private signing key immediately invalidates outstanding cursors, and traversal restarts from the collection resource.

The Events collection performs one prepared oldest-first read for an exact principal/client namespace, finite page size, optional internal sequence checkpoint, and optional exact type. The type-aware index keeps filtering bounded rather than discarding rows after retrieval. `GET /events` exposes only validated immutable event fields and translates the internal sequence into a version-1 15-minute AES-256-GCM cursor. Sequence zero represents an empty stream safely. A separate key domain derives from private signing-key material, while authenticated data binds the Events resource, issuer, key ID, exact principal, OAuth client, and filter. The token exposes none of those values or its checkpoint. Canonical encoding, shape, integer, and lifetime checks fail closed; rotation invalidates outstanding cursors and no cursor table or process-memory state exists. HTML and hypermedia share this operation model, and every successful response is no-store.

D1 access is implemented with narrow repositories and prepared SQL statements. The project does not use Drizzle ORM or Drizzle Kit: reviewed SQL lives in `db/migrations/`, the required-table manifest lives in `db/schema.ts`, and `build/sites-migrations.ts` packages the reviewed statements plus the Sites migration journal into `dist/.openai/drizzle/`. `npm run db:check` prevents the manifest, migration history, and packaged ordering from silently diverging. Sites applies the deployment artifact migrations; request handlers never issue schema DDL.

Migration `0012_service_clients.sql` distinguishes human and service principals plus interactive and service OAuth clients without weakening existing storage foreign keys. Service registration atomically creates the client and one internal principal row; only a hash of its one-time-displayed secret is stored. User lookup, identity statistics, privacy fallback, account deletion, UserInfo, interactive grants, and human claims exclude service principals. Service clients have no redirect URI or browser origin and accept only enabled AittaDB storage and Events scopes. They never receive identity claims, an ID token, or a refresh token.

Migration `0014_browser_session_event_scopes.sql` idempotently seeds the three Events scopes for the reserved browser client. Runtime policy remains authoritative: the seed neither enables Events nor exposes the client and cannot permit an Events scope or route while `FEATURE_EVENTS_ENABLED` is false.

Local-user resolution uses the trusted identity's exact email as its existing case-sensitive key. D1 generates a candidate UUID and executes one prepared `INSERT ... ON CONFLICT(email) DO UPDATE ... RETURNING` statement, so concurrent first requests either commit that candidate or return the already committed canonical row. A conflict preserves the UUID, email, and creation time while updating only display name and update time. The repository accepts only one successful, structurally valid returned row matching the requested identity metadata; absent, malformed, multiple, or unsuccessful adapter results fail closed. A retry after a commit whose response was lost returns the committed UUID. The test-only memory repository keeps equivalent lookup-through-insert behavior without an intervening `await`.

Account deletion has public request and coarse-status operations plus durable job, authorization-gate, bounded purge, coordination, clean-finalization, and post-deletion isolation primitives. `POST /account/deletion` starts only the current eligible local account and issues a distinct encrypted seven-day status handle on first acceptance. Content-negotiated `GET /account/deletion` validates that handle against its separate purpose, issuer, key ID/material, and exact trusted Sites email before repository work, then resolves the encrypted old subject directly for one exact job read. It never locates or creates identity by email. Missing, expired, tampered, wrong-key/issuer, and switched-account handles perform no D1, R2, cleanup, rate-limit, or coordinator work. Valid output maps internal `retryable` to public `retry` and otherwise exposes only pending, running, or completed with one state-valid refresh/recovery action; the completed status action offers only Sites sign-out and never advertises or creates a replacement identity. There is no deployment-wide deletion or special re-registration route. Migration `0008` stores one `WITHOUT ROWID` row keyed by immutable local subject, with pending, leased running, retryable, and terminal completed states. Idempotent start never resets an existing row. Claims use five-minute leases and increment an attempt used by retry/finalization compare-and-set transitions; stale workers cannot finalize reclaimed work. The table intentionally has no user foreign key so a minimal completed tombstone can survive removal of the user row. After clean completion removes the user and exact-email index, ordinary identity resolution creates one new UUID and empty namespaces for a later request with that email; repeats retain the new UUID. Old grants, credentials, consent, revocation attribution, administrator submissions, records, files, events, and status state cannot reconnect it. Previously issued access and ID JWTs may remain signature-valid for the former subject until `exp`, but AittaDB rejects them for access and they cannot identify the replacement subject.

The internal credential/grant repository removes at most 100 exact-subject rows per call in deterministic child-before-parent phases and returns aggregate progress only. It includes administrator submissions explicitly rather than relying on foreign-key cascades. It requires an existing deletion job, retries safely after any committed phase, and never deletes clients, users, storage, audit/rate state, configuration, or signing material. Browser access credentials remain unpersisted and are invalidated by the gate. Migration `0009` adds nullable subject ownership to access-token revocations; unattributable legacy rows are retained.

The independent account-record repository also requires the exact deletion-job row, then atomically removes at most 100 rows across transaction receipts, `bounded_storage_records`, and legacy `storage_records`. Receipts are selected first in deterministic client/time/hash order, bounded records next in client/collection/ID order, and the remaining budget uses legacy client/key order. Committed absence is durable progress, so no cursor or progress row is required; an exact multiple converges through one final empty batch. `{deletedCount, done}` discloses no key or namespace. Usage falls only by deleted application-record items/bytes while retained files keep their usage. Other subjects and every non-record table are outside the batch; a failed statement rolls back all three owned row families. See `docs/account-deletion-jobs.md`.

The account-event repository requires the exact human subject's running attempt and unexpired lease, then removes at most 100 immutable `application_events` rows in deterministic client/sequence order. Row absence is its durable resume marker and an exact multiple requires a final empty call. One prepared D1 deletion repeats the claim and `principal_type = 'user'` checks, so stale workers and synthetic jobs for service principals cannot delete events. Other subjects and service namespaces remain untouched. Migration `0016_account_deletion_events.sql` adds an event-specific terminal-state guard without replacing the existing completion guard, and runtime finalization independently requires event absence. Migration `0013` plus repository admission prevent new events after deletion starts. The memory repository has equivalent lease, ordering, isolation, and completion checks. See `docs/account-deletion-jobs.md`.

The account file purge is an internal protocol-independent primitive with no HTTP, HTML, hypermedia, or OpenAPI operation. Before mutation it requires the exact subject's running claim attempt and unexpired lease. Each call stages at most 25 files in deterministic client/key order. One [transactional D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch) inserts an owner-bound repair before deleting exact metadata; the repair processor globally rechecks references before R2 retirement. A foreign-owner reference is a conflict that preserves the bytes and blocks finalization. R2 or D1 uncertainty leaves durable retry state. Results contain aggregate counts only.

`coordinateAccountDeletionBatch` claims at most one job and advances at most 25 expired fences, 100 credential/grant rows, 100 records, 100 events, and 25 files per invocation. Committed absence is the durable cursor; interruption and exact batch multiples converge through retries. Migration `0010` adds the fence table, subject-retirement write triggers, and fail-closed completion triggers. Migration `0011` promotes only canonical 43-character SHA-256 base64url audit actor attribution from generic JSON to a nullable column indexed by actor hash, creation time, and event ID; malformed legacy attribution becomes null and its JSON member is removed. Finalization clears at most 100 exact-subject actor attributions in that deterministic order before conditionally removing the user and completing only the exact unexpired attempt after every owned credential, grant, record, event, file, fence, repair, and administrator submission is absent. Audit rows, unrelated actor attributions, and five-minute rate counters remain. A partial unlink commits without removing the user; an uncertain response is reconciled by observing the clean terminal state. The memory repository applies the same invariant. Only the linkable local UUID, coarse state/attempt, and timestamps remain as the permanent idempotency/security tombstone. See `docs/account-deletion-jobs.md`.

`src/subject-access.ts` owns one fail-closed invariant: no deletion row means active, while every persisted state, including the completed tombstone, means inactive for the old subject. Token issuance checks it before signing or creating refresh state. Access-token verification checks it after cryptographic and token-purpose validation but before any consumer can disclose UserInfo or storage or perform namespace rate limiting/mutation. Refresh exchange consumes the presented one-time token, then checks the same gate before signing credentials or persisting a successor. Current-session token issuance and `/session` also use it. Protocol adapters translate only its typed denial into generic `login_required`, `invalid_token`, `invalid_grant`, inactive introspection, or forbidden administration responses; repository failures remain generic server failures. The deletion-start domain function rejects subjects in `ADMIN_SUBJECTS` before repository mutation. Subject and internal job metadata remain private: request surfaces expose only protected input and coarse acceptance, while status surfaces expose only pending/running/retry/completed. Neither serializes the former UUID, email, attempts, timestamps, counts, client/namespace values, credentials, or storage identifiers. See `docs/account-deletion-jobs.md`.

It never stores or forwards ChatGPT credentials. Downstream `sub` values are locally generated immutable UUIDs.

Application assembly injects an `UpstreamIdentityProvider` through every identity-aware route. The deployed `createAittaDB` entry point always selects the Sites adapter, which reads only documented request headers. No runtime binding or environment mode can select a mock identity. Integration tests call `createAittaDBWithStore` with a provider defined under `tests/`, keeping synthetic users outside the Worker dependency graph.

Application URIs identify resources, not presentation-specific route trees. `Accept: text/html` selects semantic HTML; `Accept: application/vnd.aittadb+json; version=0.1` selects the versioned hypermedia representation; `application/json` is the compatibility representation. JSON documents contain `data`, semantic `links`, and currently authorized `actions`. HTML renders the same state and transitions as links, forms, lists, tables, and readable outcomes. Both representations call the same authorization, validation, domain, and repository units; representation selection never depends on `User-Agent`.

Application negotiation parses media-range quality, specificity, exclusions, wildcards, quoted parameters, and the preview version. No acceptable application representation returns `406`; vendor errors retain the vendor media type. Standards-defined OAuth/OIDC responses and file-byte delivery keep their protocol or binary media types instead of being wrapped.

The public root advertises real service operations in both representations. Its sign-in or sign-out action reflects the trusted server-side ChatGPT Sites identity signal. `/session` is the protected upstream-authentication boundary: it creates or retrieves the D1-backed local user, requires that subject to have no deletion job, and returns that same identity as HTML or JSON. For an eligible non-administrator it also renders one `POST /account/deletion` control with CSRF plus a purpose-specific AES-GCM value bound to issuer, current subject, and exact trusted email. POST resolves identity again, performs only an exact-email read-only user lookup, applies the shared pre-body origin policy, a 1 KiB form/JSON bound, explicit phrase, CSRF, per-IP/global rate limits, and atomic first-start. Before that start it seals a separate status handle whose HKDF info and AES-GCM additional data bind a distinct purpose, issuer, key ID, and exact trusted email while ciphertext carries the old subject and seven-day lifetime. Only a created job receives the scoped status cookie, one caught `waitUntil` coordinator nudge, and a coarse no-store `202`; stale identity, administrator, replay, and token failures remain generic. GET validates the handle before any store-availability failure or repository call. A valid noncompleted read requires D1, R2, and `waitUntil`, performs one exact job read, and schedules one caught coordinator pass; completed reads and every error schedule none. When enabled, `/statistics` performs one prepared aggregate count and exposes only `identity_count`; it cannot enumerate identities or reveal personal fields. When disabled, the root omits its HTML and hypermedia controls and the route returns the same content-negotiated `503 feature_unavailable` contract before checking D1 availability, querying identities, or scheduling cleanup. Browser representations never maintain a second user, grant, token, or storage model.

`GET /privacy` is one public resource with accessible HTML and versioned hypermedia JSON representations. Explicit `PRIVACY_CONTROLLER_*` and `PRIVACY_CONTACT_*` values take precedence. If required controller/contact data is missing, the handler resolves only the first canonical UUID in `ADMIN_SUBJECTS` through the user repository and may publish that user's stored email and optional display name; it never emits the UUID, allowlist, or other user/configuration fields. If neither source yields a usable controller and contact, both representations fail generically with `503`. The baseline content and retention disclosures are maintained in `docs/privacy.md`.

Storage browser representations are resource-oriented. A collection `GET` renders a list or explicit empty state and item-navigation controls. `GET /storage/files` also renders a native file input; same-origin JavaScript may add accessible drag-and-drop feedback, but never changes the operation or security boundary. `POST /storage/files` creates a file under a server-generated logical key and returns canonical storage state with an item `Location`. Bearer JSON/hypermedia and explicit-token HTML retain `201 Created`. A successful signed-in HTML collection upload accepts an absolute `Location` only from the request or configured issuer origin, validates its exact item path, and constructs `303 See Other` on the request origin. A missing, malformed, or foreign target safely retains the rendered `201`. This lets storage emit its issuer URL while keeping custom-domain browser navigation same-origin. The redirected `GET` owns item details and actions, making refresh read-only. An item `GET` renders read/download, `PUT` create-or-update, and `DELETE` controls valid for only that URL key. Protected browser actions post to that same collection or item URL with a fixed method override. The adapter validates same-origin and CSRF state, rejects method/resource mismatches, derives item keys only from URLs, and invokes `storageEndpoint` through a synthetic `Authorization` header.

In current-session mode, the adapter maps the trusted Sites identity to the local user and issues a minimal short-lived credential for the reserved `aittadb-browser-session-v1` client. In token mode, it uses the explicitly submitted AittaDB token. The reserved client is migration-seeded, hidden from client lists, immutable through administration, and rejected by every external OAuth entry point. Its user/client ownership keys keep the durable signed-in AittaDB namespace separate from every third-party application, including applications used by the same user. `/auth-ui.js` only hides inactive form controls and upgrades collection navigation to the canonical item action; server-side validation and the no-JavaScript path remain complete.

All browser forms use a double-submit CSRF token in a host-only, secure, `HttpOnly`, `SameSite=Lax` cookie. A valid token is reused while its 15-minute cookie is active, including across ChatGPT sign-in return, so forms opened in concurrent tabs do not invalidate each other. Rendering replaces malformed cookie values with fresh high-entropy tokens. One pre-body route classifier covers every enabled HTML mutation adapter: protocol forms selected by `Accept: text/html`, browser-only session/device/consent/admin routes, and form-encoded or multipart storage adapters. It rejects an invalid origin before body pulls, rate counters, repository or R2 calls, and maintenance scheduling. The shared origin policy accepts an exact configured issuer origin even when Sites exposes an internal dispatch URL. It accepts opaque `Origin: null` only when `Sec-Fetch-Site` is exactly `same-origin`; missing, malformed, foreign, same-site, and cross-site signals fail closed. A valid origin then permits bounded form parsing and the independent canonical cookie/form CSRF comparison. CSRF failures still occur before domain mutation, and reloading renders a usable retry form. `/session` and `/privacy` remain GET-only; their current representations expose no local mutation form. Standards-defined machine OAuth requests and raw bearer storage uploads do not enter this browser-form classifier.

URL-encoded forms, record JSON, and raw file bodies use the shared stream-bound reader before buffering. Browser multipart upload wrappers additionally require trusted Sites identity before parsing, including explicit-token mode; an absent or malformed identity returns before pulling the stream, durable rate limiting or cleanup, storage-repository work, or R2 access. Raw bearer file APIs remain independent of browser sign-in. Record JSON reaches the same 64 KiB parser and D1 repository as REST `PUT`; file bytes reach the same 10 MiB canonical `POST`/`PUT` path even when `Content-Length` is absent, malformed, or untrustworthy. Raw overflow returns `413`; a failed raw stream returns `400`; neither reaches R2 or D1 file metadata. File replacement is copy-on-write, and each metadata create, replace, delete, or rollback uses D1 compare-and-set against the observed physical key. A stale replacement or delete returns `409` without changing or deleting a newer winner. Any losing or rollback object that cannot be retired immediately is durably queued for private orphan repair; TASK-119 rechecks global references before deleting bytes. Isolated D1 or R2 failures trigger bounded cleanup or rollback.

D1 and R2 have no shared transaction. When a file mutation and its bounded compensation cannot resolve a physical object, the storage domain records an internal delete-if-unreferenced candidate through `AuthStore.recordStorageFileOrphanRepair`. Migration `0006_storage_file_orphan_repairs.sql` stores only the generated R2 key, owning local-user/client namespace, and first/last activity timestamps. The physical key uniquely deduplicates repeated recording; a conflicting namespace cannot reassign an existing row. The table intentionally has no user/client foreign key so a repair remains durable across later account or client lifecycle work. It stores no logical key, content metadata, digest, error text, credential, or secret and has no HTTP, hypermedia, or OpenAPI surface.

The repair row is also an exclusion lock: every file-metadata upsert refuses its physical key while the row exists. Once-per-minute durable-route maintenance lists at most 25 rows in deterministic `updated_at`, `created_at`, and physical-key order. One D1 statement classifies each candidate as missing, globally referenced, or orphaned using the physical-key index. Missing candidates are skipped; referenced candidates retire only their queue row and preserve R2; only an explicit orphan classification reaches R2 deletion. The still-present row prevents reattachment until deletion and owner-bound completion. A failed R2 or D1 step leaves or re-touches the row, rotating it behind older work and allowing an idempotent later retry. Concurrent processors may repeat an orphan deletion but cannot reinterpret a removed referenced row as deletable. Migration `0007_storage_file_orphan_repair_order.sql` indexes the global reference check and finite fair ordering. The processor returns only aggregate internal counts and has no caller-visible route.

Authorization-request decisions, authorization-code consumption, approved-device consumption, and refresh-token consumption are conditional D1 updates whose affected-row count gates success. The remembered-consent `GET` continuation and explicit approval or denial `POST` all use the same pending-only authorization-request transition. A repeated or concurrent loser receives a local `invalid_request` response without a client redirect, callback URI, authorization code, or preserved state. Device polling updates only polling metadata and cannot restore a stale terminal status. Device and short user codes are persisted only as hashes; the short display code returned by RFC 8628 is reconstructed for consent from the matching same-origin browser submission, and migration `0004` blanks legacy display values. JWT validation accepts only ES256 and the configured `kid`, verifies the signature, and enforces exact issuer and audience plus expiration, issued-at, and not-before boundaries. Authorization Code ID tokens retain the registered client ID as audience and the original OIDC nonce. Client Credentials authenticates only a service client, issues the normal short-lived access JWT with `sub` and `aud` equal to that client UUID plus `subject_type=service`, and returns no ID or refresh token or user claim. Every access-token consumer requires `token_use=access`; storage additionally validates the matching active human or service principal, UserInfo requires a human `sub` plus `openid`, and authenticated confidential/service introspection reports active only for a valid access token issued to that same client. Revocation authenticates the owning client, revokes an opaque refresh token's family, or records a verified access-token `jti`, with standards-compatible success non-disclosure and hint fallback.

Administrator access resolves the current trusted Sites identity to its AittaDB local user and requires that canonical UUIDv4 in `ADMIN_SUBJECTS`. There is no caller-supplied administrator key or unlock route. Same-origin and CSRF checks independently protect every mutation, and only allowlisted representations contain client data or administrative actions. HTML forms, versioned hypermedia actions, and POST validation use one operation policy: active clients can be disabled, disabled clients can be enabled, confidential and service clients can rotate secrets, and every listed client can revoke grants. An operation omitted for the current state or type is also rejected server-side. Each mutation atomically claims the submitted one-time token hash in D1 before changing client state. JSON returns the immediate no-store result. HTML uses Post/Redirect/Get; a five-minute encrypted, `HttpOnly`, `SameSite=Strict` cookie carries the result to one atomically gated GET, preventing refresh or replay from repeating the mutation or redisplaying a secret. The cookie contains no URL-visible plaintext, D1 stores no result or secret, and only the client-secret SHA-256 hash remains after consumption. Client-mutation audit records contain bounded event names, a fixed subject-authorization source, and hashed actor/client references; repository redaction still removes credential-like fields before persistence. Subject allowlisting does not remove email-reassignment risk because the user repository still locates that UUID by upstream email.

The self-hosted Swagger UI reads the canonical OpenAPI document, but its request interceptor targets the origin that serves the viewer. This keeps "Try it out" same-origin on custom domains and avoids sending credentials to a stale or legacy server URL.

Public metadata, health, discovery, JWKS, OpenAPI, documentation, and stylesheet requests do no D1 work. Enabled `/statistics` is a deliberate exception and executes only its bounded aggregate query; disabled `/statistics` does no store work. `/privacy` performs at most one user lookup only when explicit public contact configuration is insufficient. Static assets pass directly to Vinext. Durable routes schedule cleanup through `waitUntil` at most once per one-minute Worker instance interval. Each run deletes at most 500 rows per OAuth, device, refresh, revocation, admin-submission, audit, rate, or application-event category. Events are selected oldest-first by their indexed expiry and internal sequence; other categories use their eligibility timestamp and deterministic `rowid` tie-breaker. Empty refresh families receive a one-hour grace period so cleanup cannot race first-token creation. Audit events become cleanup-eligible after 90 days and one-minute counters after five minutes. Event expiry defaults to seven days, is configurable up to one year for new immutable rows, and cleanup stays active while Events is disabled. Atomic counters apply per-IP/global endpoint limits and per-user/client storage limits; new keys fail closed at 10,000 rows, and a global endpoint ceiling is ten times its per-IP ceiling.

For cross-origin UserInfo, storage, and Events calls, preflight origins must belong to an active registered client and an actual bearer request must match an exact origin on its own active audience client. Token preflight uses the active-client origin index; the actual token request must match the client named by `client_id` or HTTP Basic before a code, device grant, or refresh token is consumed. Other controlled routes use the configured exact origin list; no credentialed wildcard is used. Dynamic responses receive one-year `includeSubDomains` HSTS for a production HTTPS issuer. These controls and scheduling hints do not make process memory authoritative. Persistent Events exposes feature-gated immutable publication, bounded collection/item reads, and bounded cursor-based long polling. Event update, deletion, fan-out, and background/unbounded delivery remain unavailable.
