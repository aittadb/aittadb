# Security Policy

AittaDB is experimental, security-sensitive application-backend software. Report vulnerabilities privately to Jaakko Heusala <jheusala@iki.fi>.

Do not file public issues that include working exploits, private keys, client secrets, refresh tokens, access tokens, authorization codes, device codes, cookies, or PII.

## Public Repository Secret Safety

The canonical GitHub repository is public and contains no secrets. Never commit private signing material, runtime `.env` or `.dev.vars` files, active `.openai/hosting.json` or Wrangler state, deployment credentials, generated administrator/client material, or bearer-equivalent values. Checked-in example configuration contains only inert placeholders, and test credentials are synthetic fixtures. Keep real values in ignored local files or hosted secret/configuration stores.

Run `npm run secrets:check` before committing. It deterministically scans Git-tracked paths and text without printing matched values; it is deliberately repository-specific, not a generic entropy scanner. From a complete clone, `npm run secrets:audit-history` scans every commit reachable from local and remote refs. Historical `.openai/hosting.json` revisions are reported separately as legacy public deployment metadata because Sites `project_id` values are identifiers, not credentials; the active file still stays ignored and must never become a reusable fork template.

If exposure is suspected, do not echo or paste the value. Escalate privately at once with only its category, path, and commit. Rotation or revocation requires explicit maintainer approval, as does any public-history rewrite. Deleting a value from the current tree does not invalidate it or remove it from history.

Production deployments must configure `ISSUER_URL`, `JWT_KEY_ID`, `JWT_PRIVATE_JWK`, D1 binding `DB`, R2 binding `BUCKET`, and finite storage controls through Sites secrets, environment, and bindings. Deployments enable administration only by configuring canonical local UUIDv4 values in `ADMIN_SUBJECTS`; an empty list disables it. Production deployment requires explicit maintainer approval.

The deployed application always uses the single ChatGPT Sites header identity provider. There is no production configuration, binding, or environment mode for a mock user; synthetic identities are injected only by test code that is outside the Worker module graph.

Application storage is available only through scoped operations bound to both the access token's immutable local user UUID and OAuth client ID. The same checks apply whether a resource is represented as hypermedia JSON or HTML. Collection file creation generates its logical key server-side; item updates use only the validated URL key; all R2 physical keys are generated internally.

AittaDB must never expose generic SQL/D1 access, internal authentication tables, physical R2 keys, environment values, bindings, private JWK fields, hosted secrets, or another user/client namespace. The reserved current-browser-session client is internal, non-administrable, and invalid for external OAuth flows. The public `/statistics` resource is limited to one aggregate local-identity count and must not expose identity rows, personal fields, client relationships, or storage metadata.

Storage creates and replacements are admitted by one conditional D1 statement that applies combined record/file item and byte ceilings at deployment, user, and user/client levels. File metadata transitions also compare the observed physical R2 key; stale operations return `409` and cannot overwrite a winner. The finite defaults are abuse controls, not provider-capacity guarantees. `STORAGE_WRITES_ENABLED=false` blocks creates/replacements while preserving authorized reads/deletes. Lists use bounded `page_size` and encrypted, namespace-bound cursors that expose no position, namespace identifier, or signing secret. Rotating the private signing-key material immediately invalidates outstanding cursors. Collections disclose only current-namespace usage and limits.

One-time OAuth transitions are atomic D1 compare-and-set operations. Remembered-consent continuation and explicit authorization approval or denial compete for the same pending request; only the winner can redirect, and a loser fails locally without reflecting the callback or state. JWT verification is limited to ES256 and the configured key ID and enforces signature, issuer, audience, expiration, issued-at, and not-before claims. Every bearer consumer rejects ID tokens; UserInfo additionally requires `openid`, and confidential-client introspection reports only a valid access token for that client as active. Refresh reuse revokes its family, and revocation is client-bound. Once account deletion starts, an internal indexed batch can remove at most 100 exact-subject credential/grant rows in child-before-parent order; it requires the deletion job, preserves all clients and other subjects, and resumes idempotently after interruption. Stateless browser credentials remain unpersisted and are invalidated by the deletion gate. Atomic counters limit OAuth, administration, and storage, including per-user/client storage traffic. The table admits at most 10,000 keys and fails closed for new keys at that ceiling. Cleanup runs once per minute per Worker instance, deletes at most 500 rows per category using relationship indexes, gives new empty refresh families a one-hour grace period, and retains one-minute counters for five minutes. Endpoint global limits are ten times per-IP limits.

Browser mutations require a canonical CSRF cookie/form token pair and an independently verified same-origin signal. One route-level classifier rejects missing, malformed, foreign, cross-site, and unauthorized opaque origins before request-body pulls, rate-limit or repository work, R2 access, or maintenance scheduling. Accepted URL-encoded and JSON bodies then pass the shared streaming byte bound before parsing or any repository call. Declared overflow fast-fails, while missing, malformed, and undersized `Content-Length` values remain non-authoritative; overflow returns `413` and a failed request stream returns `400`. A valid bounded CSRF session survives concurrent forms and ChatGPT sign-in return; stale, mismatched, or malformed CSRF state fails before domain mutation, and a fresh form can retry. Browser multipart also requires trusted Sites identity before parsing, then all accepted bodies are stream-bounded regardless of `Content-Length`. Machine OAuth and raw bearer storage requests remain outside this browser-form classifier. Production HTTPS responses include HSTS. Cross-origin UserInfo/storage requests require an exact origin on the active token-audience client. Token exchange binds the submitted active client and exact origin before consuming a code, device grant, or refresh token. Disabled or missing clients fail closed.

Administrative access requires a current trusted ChatGPT sign-in inside ChatGPT Sites whose immutable local UUID is in `ADMIN_SUBJECTS`. There is no administrator password, key header, unlock form, or separate admin-authentication cookie. Same-origin and CSRF checks protect mutations independently, and an atomic one-time submission claim prevents mutation replay. Successful HTML mutations use Post/Redirect/Get; an encrypted, subject-bound, short-lived `HttpOnly`, `SameSite=Strict` cookie carries the result to one atomically gated read. It never puts a generated client secret in a URL or durable plaintext storage. Mutation audits contain only bounded event data and hashed actor/client references; credential-like fields are redacted. Do not treat UUID allowlisting as protection from email reassignment: AittaDB still locates the UUID by upstream email.

Device codes are high entropy and stored only as hashes. Short user codes are also hash-only at rest: the standard response returns the display code, the same-origin verification form supplies it when rendering consent, and migration `0004_security_indexes.sql` blanks legacy display values. AittaDB does not write either code to audit records.

File operations compensate isolated D1/R2 failures, but the services do not share a transaction. Unresolved objects enter private owner-bound repair state that blocks metadata reattachment; finite background batches retain globally referenced bytes and idempotently retry deletion of unreferenced objects. A total D1 outage can prevent initial recording; public responses remain generic and never reveal object keys, bindings, or backend errors.

## Current Source Status

The current source addresses aggregate ceilings, pagination, atomic rate counters, bounded indexed cleanup, active-client CORS and UserInfo checks, HSTS, subject-allowlisted and replay-safe administration, hash-only short device codes, concurrent R2/D1 compensation, pre-auth multipart, client-bound token CORS, and encrypted cursors. Earlier source already contains affected-row-gated code/refresh consumption, client-bound revocation, JWT purpose checks, tenant-scoped storage, and streaming request bounds.

These statements describe source and automated-test controls, not live acceptance evidence. Every release candidate must separately verify the exact deployed commit in ChatGPT Sites, including a two-user/two-client isolation exercise when two identities are available, and record platform-limited evidence in `PLAN.md` and its pull request. Ordinary-user and administrator identity still depends on an upstream email because Sites documents no stable subject; an address reassignment can inherit the prior AittaDB UUID, namespaces, and administrator allowlist membership. Sites D1/R2 numerical capacity also remains unpublished, and the cross-service D1/R2 partial-failure case above remains operationally irreducible without a shared transaction.
