# AittaDB Backlog

This file records uncommitted implementation ideas. An item here is not a current capability, release commitment, delivery schedule, or stable API contract. Stable `BACKLOG-NNN` identifiers must not be renumbered or reused.

`PLAN.md` is the auditable list of accepted implementation work. `ROADMAP.md` describes public product direction. Before work starts on a backlog idea, define the integrated contract, implementation, tests, documentation, failure behavior, and acceptance evidence as a new unchecked `PLAN.md` task. The backlog item remains unchecked until the idea is either promoted through that process or explicitly retired with a documented replacement.

A backup or synchronization feature must operate only on the authenticated user's data within the authorized OAuth client namespace. It must never export, import, mirror, or reveal AittaDB authentication tables, other users' or clients' data, physical R2 keys, bindings, environment variables, signing material, hosted secrets, or deployment metadata. ChatGPT Sites D1/R2 capacity and operational limits remain provider-controlled and numerically undocumented.

- [ ] BACKLOG-001: Define namespace-scoped point-in-time backup export for an authenticated user's authorized application records and files, including a versioned manifest, bounded D1/R2 snapshot-consistency semantics, integrity metadata, caller-controlled encryption, resumable transfer, retention and expiry rules, and explicit exclusion of AittaDB internal state and secrets.
- [ ] BACKLOG-002: Define verified backup restore into the same authorized user/client namespace, including manifest and content-integrity checks, ownership proof, dry-run reporting, idempotent retries, collision policy, partial-failure recovery, quota and rate enforcement, and no ability to choose or overwrite another namespace.
- [ ] BACKLOG-003: Define incremental backups after a verified checkpoint, including opaque durable cursors, ordered changes, tombstones for deletions, cursor expiry and retention, bounded batches, idempotent replay, and behavior when history is no longer available.
- [ ] BACKLOG-004: Define opt-in live synchronization for authorized records and files, including resumable ordered delivery, idempotency keys, backpressure, rate and quota controls, connection recovery, an ordinary polling fallback, and integration with persistent Events only after the Events contracts exist.
- [ ] BACKLOG-005: Define live-sync conflict and deletion semantics, including resource versions or entity tags, concurrent update detection, deterministic conflict reporting, explicit resolution choices, tombstone lifecycle, and protection against silent destructive overwrite.
- [ ] BACKLOG-006: Define privacy-preserving backup and synchronization administration, including user-visible status, bounded audit events, recovery drills, restore verification, failure alerts, key-loss guidance, provider-limit failures, and redaction of identities, credentials, object keys, and secret material.
